## 1 · 根因

`packages/gui/src/main/window.ts` 的 `createDesktopLyricsWindow`：

```ts
win.setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true });
```

这是 Electron 文档里让一个窗口盖住全屏应用的正路。它**顺手**还做了一件文档写在另一个字段下面的事：对**进程**执行
`TransformProcessType(kProcessTransformToUIElementApplication)`。

UIElement 应用没有 Dock 图标，也没有菜单栏。

**探针**（本机，仓库自己的 Electron 43.2.0；`app.dock.isVisible()` + 进程外的 `lsappinfo`）：

| 时刻 | `dock.isVisible()` | `lsappinfo ApplicationType` |
|---|---|---|
| 主窗口起来 | `true` | `Foreground` |
| **执行那一行** | **`false`** | **`UIElement`** |
| 销毁歌词窗（= 关掉桌面歌词） | `false` | — |
| 之后再 `mainWindow.show()` | `false` | — |

**三件事要说清楚**：

1. **受害的是进程，不是窗口。** 所以 Dock 图标、菜单栏、Cmd+Q 一起没有；而进程活着、歌照放——用户看到的正是「没了，但是没退出」。
2. **关掉桌面歌词不还回来。** transform 从来不属于那个窗口，没有任何一条路径把它转回 foreground。只有重启进程才行。
3. **它能把应用变得摸不到。** 主窗口是「红叉 = 隐藏」（M4 的既有设计，为了让播放和 SSE 命令通道活着）。没有 Dock 图标就没有「点回来」，没有菜单栏就没有 Cmd+Q——**先开歌词、再点红叉，这个 lark 在 UI 上就没有入口了**，只能强制退出。

**现在已经装了 0.5.0 的人怎么自救**：强制退出（`⌘⌥Esc` 或活动监视器）再打开。transform 不落盘，重启即正常。装上 0.5.1 之后不需要做任何事。

## 2 · 修法

Electron 43 有 `skipTransformProcessType`，就是为跳过这次进程转换而存在的：

```ts
win.setAlwaysOnTop(true, 'screen-saver');
win.setVisibleOnAllWorkspaces(true, {
  visibleOnFullScreen: true,
  skipTransformProcessType: true,
});
```

两个 collection behavior（`canJoinAllSpaces` / `fullScreenAuxiliary`）照设，只是不动进程。**已实测：加上之后 `dock.isVisible()` 保持 `true`。**

**为什么不是别的两条路**：

- **不传 `visibleOnFullScreen`** —— Electron 走 foreground 分支，Dock 一定在，但歌词不再出现在别的应用的全屏 Space 上。而「看视频的时候看词」正是 `window.ts` 那段注释说这个设计要的东西，等于用一个功能换另一个功能。
- **`type: 'panel'` 非激活面板** —— overlay 盖全屏的正路，也不需要降级进程，但它改窗口类型，控制条的点击与 hover 要整套重验。**留作后手**：如果 §3 判据 2 发现全屏覆盖丢了，再升级到这条。

**风险点，说在前面**：Electron 做这次 transform 的理由是「ensure the correct behavior」。跳过它之后**全屏覆盖是否还成立，只能在屏幕上验**（§3 判据 2）。

## 4 · accept-gui 加三条（**已定：加**，用户 2026-08-28）

**为什么**：0.5.0 带着这个 bug 通过了 129/129。判据 1 是**源码**守卫，它只答「有没有人把那行改回去」；它答不了「Electron 换了行为」，也答不了「别处又有代码降级了进程」。**这一版的教训正是「碰平台的那几行没有判据」**，所以补一条看**产物**的。

**怎么做**：`lsappinfo info -only ApplicationType <pid>` 从**进程外面**读 `Foreground` / `UIElement`——这是这个 harness 唯一站得住的观察点，`app.dock.isVisible()` 在主进程里，而 CDP 只够得到渲染进程。accept-gui 本来就启动真 GUI 产物并拿得到 `gui.pid`。

**落成三条 `check`，不是一条**——中间那条是这一版最该记住的形状：判据自己的前置条件，也要能红。

| check | 断言 | 为什么必须有它 |
|---|---|---|
| `7 · the live config was readable (this criterion needs it)` | `GET /config` 真的答了 `desktop_lyrics` | 判据自己的前置条件。读不到就发不出有意义的 publish，后两条会绿得毫无内容 |
| `7 · the lyric window opened` | CDP `/json/list` 里出现 `lyrics.html` 的 page target | **没有它，第三条就是空判据**——publish 悄悄没生效的话，进程当然还是 foreground，判据绿着却什么都没量。这是 0.5.0「判据没走到会出问题的那条路」那一课 |
| `7 · the open lyric window left the GUI a foreground app` | 开窗前后 `ApplicationType` 都是 `Foreground` | 就是这一版修的东西 |

**计数**：`accept-gui` **15 → 18**，五套合计 **129 → 132**。

**第一版写红过一次，值得记**：这三条放在判据 6（daemon 重启 + token 轮换）之后，而 harness 的 `api` 助手闭包着**重启前**的旧 token——`GET /config` 答 401，`data` 是 `undefined`，整个套件当场崩在解构上。改用判据 6 自己建的 `newAuth`，并把「配置读到了没有」提成一条明判据：**崩溃是运气好，静默取空才是要防的那一种**。

**它不答什么**（写进判据的注释里）：窗口是走 preload bridge 开的，不是走设置页，所以它**证明不了用户点得到**——那半边归 `2026-08-28-manual-check.md`。这是「判据验过 ≠ 用户点得到」的原样。

## 7 · 多 P 选集与分P命名（待评审）

### 7.1 现状（三端各不相同，这是设计的起点）

| | 桌面 | 手机 | CLI |
|---|---|---|---|
| **识别** | `POST /download/parse`（daemon 在线） | **离线** `readLines` / `recognise`（portable），只有 `b23.tv` 要一跳 | 走 daemon |
| **多 P 无 `?p=`** | `preflightSingle` 取 `pagelist` → 有 LLM 就 `choosePage` **让模型选一个**，模型答不出退回 **1**；无 LLM → `LLM_NOT_CONFIGURED` | 同一份 `preflightSingle`（portable），闸做成加歌页上的 inline 提示 | 同 |
| **选择 UI** | `BatchSelectModal`（只服务收藏夹/合集 + 多行的单项） | `ListPicker`（合集） | 无，也不可能有 |
| **命名** | `NamingModeDialog` | 「清洗」chip | `--naming` |

**两个问题的确切位置**：

- **选集** —— `pipeline.ts:111-125` 的 `choosePage`。「定位到第一 p」不是 bug，是 `pickPage` 的模型答案或它的退化默认。
- **命名** —— `pipeline.ts:94` 的 `const title = target.title ?? view.title;`。`view.title` 是整个稿件的标题；**分P 自己的 `part`（「烟雨行舟」）在命名链路上一次都没出现过**——`pagelist` 拿到了它（`bilibili.ts:441`），只在给模型选集时用过一次（`pipeline.ts:136`），选完就丢。

### 7.2 一个让这件事变小的发现

**多选下载不需要改线协议。** `DownloadBatchItemInput` 已经是：

```ts
{ kind: 'video'; bvid: string; page: number | null; title: string | null; naming: DownloadNamingMode }
```

- **勾了三个 P** = 同一个 `bvid`、三个不同的 `page`，一组 `POST /download/batch` 发出去。`source_key` 是 `bvid:cid`，三个 P 的 cid 天然不同，去重不会打架。
- **分P 子标题进命名** = 把 `title` 填成那个 P 的 `part`。`pipeline.ts:94` 的 `target.title ?? view.title` **会直接用它**——这正是 `fetch-list` 给合集标题用的同一个通道。

所以真正要新增的只有一件：**把分P列表拿给 UI 看**。手机 portable 直接有 `client.pagelist`，**桌面必须走 daemon** ⇒ 一个新端点 ⇒ 协议 9 → 10。

### 7.3 六件事，已定（用户 2026-08-28）

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| **a** | 展开分P 的端点长什么样 | ① 扩 `fetch-list` 收 `{type:'parts', bvid}`——但它的 `videos` 是 `{bvid,title,duration}`，没有 `page`，要给 `FetchListData` 加可选字段；② 新端点 `POST /download/parts` → `{title, parts:[{page,part,duration}]}` | **②**。分P 不是 list，`FetchListData` 的「部分成功 + error」语义对 pagelist 不成立（它一次就答完），塞进去会让两种东西共用一个说不清的形状 |
| **b** | 桌面**单条**多 P 链接走哪个弹窗 | ① 复用 `BatchSelectModal`，加一种「分P 组」；② 新开一个只管分P 的弹窗 | **①**。它已经会「勾选 + 命名模式 + 目标歌单 + 提交成一批」，分P 组和 ListGroup 是同一形状；新弹窗等于把这四件事再抄一遍（C11/C12 的老账刚付过一次） |
| **c** | **多行**里混着多 P 怎么办（你特别点的） | ① 提交前对每个 `page===null` 的都探一次 `pagelist`（贴 20 条 = 20 次请求）；② 弹窗里每个多 P 项显示一颗「展开分P」按钮，**点了才请求**；③ 多行场景一律不展开，维持旧行为 | **②**。既不让贴 20 条的人等 20 次网络，也不让多 P 在多行里被静默地当成 1 P。**它同时也是「和之前行为兼容」的答案**：不点展开 = 旧行为 |
| **d** | 弹窗默认勾选什么 | ① 一个都不勾；② 全勾；③ 只勾第 1 P | **①**。你要的是「人来接管」，而默认全勾会让一次误点下载几十首 |
| **e** | **CLI 怎么办**（没有弹窗，这是兼容性的硬点） | ① 保留现状（有 LLM 就模型选一个，没有就报错让加 `?p=`）；② 加 `--part <n,m>` / `--all-parts`，不给就报错；③ ①+② 都要 | **③**。CLI 的旧行为是「和之前兼容」的一部分，不能因为 GUI 有了弹窗就把它拿掉；但既然人已经能选，给 CLI 一个不靠模型的表达方式是顺手的 |
| **f** | `original` 模式下，多 P 的「原样」是什么 | ① `part`（分P 标题）；② `view.title`（整稿标题）；③ `整稿标题 - part` | **①**。`original` 的承诺是「同一个链接永远得到同一个名字」，而对一个具体的 P 来说，最诚实的原样就是它自己的标题。**但这会改掉现有带 `?p=` 下载的命名结果**——旧的会得到整稿标题，新的会得到分P标题，**这条我最没把握，尤其对「和之前行为兼容」** |

**拍板结果**：**a ②**（新端点 `POST /download/parts`）· **b ①**（复用 `BatchSelectModal`）· **c ②**（按需展开）· **d ①**（一个都不勾）· **e ③′**（**改成必须 `--part`，拿掉模型选集**）· **f ①**（用分P 标题）。a / b 用户未反对，按建议走。

🔴 **e 是一次破坏性变更，代价要写明白**：`pickPage` 与 `multiPPrompt` **三端一起下岗**，模型不再参与选集。今天「多 P 链接 + 配了 LLM」能跑通的命令，**从这一版起会报错**，要求人给出 `?p=` / `--part` / 在弹窗里勾。换来的是三件事：选集不再需要 LLM（今天没配 LLM 连多 P 都下不了）· 「贴链接不走模型」对多 P 也成立 · 少一条模型答错就静默下错歌的路径。**错误码要换**：这不再是 `LLM_NOT_CONFIGURED`（配了也一样不行），新增一个「多 P 未指定」的码——这是协议 9 → 10 的第二个理由。

🔴 **f 的边界，我按这样理解，若不对请纠正**：**多 P 视频用 `part`，单 P 视频维持 `view.title`**。单 P 稿件的 `part` 常常是「1」或文件名这类没有意义的东西，而且单 P 本来就没有 `?p=` 语义差；把它一起改会制造一堆无谓的不兼容。所以不兼容只发生在**真正的多 P 视频**上——那也正是你要修的场景。

### 7.4 命名要改的那一处

「综合判断」需要模型**同时看见两个标题**：歌手在整稿标题里（`【司夏　古风歌曲合集】`），歌名在分P标题里（`烟雨行舟`）。现在 `inferSongInfo(deps, title, '', view.ownerName, ctx)` 只收一个。

- `prompts.ts` 的 `cleanNamingPrompt` payload 从 `{title, user_input, uploader}` 扩成 `{title, part, user_input, uploader}`；提示词说明 `part` 存在时通常才是歌名、`title` 通常带歌手与合集名。
- `pipeline.ts` 的 `resolveTarget` 把 `source.pages[page-1].part` 传下去（`normalizeSourceOnline` 已经把 `pages` 带回来了，**不用多发一次请求**）。
- 单 P 视频 `part` 常常等于整稿标题或为空 ⇒ 传空串，行为与今天一致。

| 6 | 手机端同一条链接得到同一组分P，且**离线解析这一条没有被破坏**（多 P 展开是唯一要联网的一步） | 单测 + 真机 |
| 7 | CLI 的旧行为逐字不变（决策 e 定了再补新判据） | 单测 |
| 8 | 没配 LLM 时，多 P 选集**不再需要模型**（现在是 `LLM_NOT_CONFIGURED`） | 单测 |

### 7.6 还没答的

- **模型选集（`pickPage` / `multiPPrompt`）留不留？** 决策 e 选 ① 或 ③ 就得留（CLI 要用），选 ② 就可以删。
- **手机端的展开 UI 用什么**：`ListPicker` 是合集用的，形状上可复用，但手机端没有 router、没有手势栈，**多选长列表在手机上是另一个交互问题**——这一条我建议单独看一眼真机再定。
- **决策 f 若选 ①**，要不要给已经下过的歌做任何事？（我的建议：**不做**，命名是下载那一刻的快照，历史不追溯。）

### 7.7 分批
