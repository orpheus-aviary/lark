## §0 范围

**做**：① **选择模式**（长按进入 · 计数与全选 · `BackHandler` 退出）+ 四个批量动作（固定 / 取消固定 · 加入歌单 · 删除 · 歌单详情里的移出歌单）；② **行菜单补齐三项**——复制链接 · 用 app 打开 · **更改链接**（含四分支归一化与「自动识别」预览）；③ 为 ② 把桌面 daemon 里那两段逻辑**提取进 portable**（§1.2）。

**不做（本批）**：歌词管理（重新下载歌词 / 删除歌词，桌面有、手机连一个歌词管理入口都还没有）· 复制歌曲 ID（决策 f）· 拖柄重排（N2 已决定不做）· 歌单导入（N6）· 同步（N5）· **锁屏暂停键接进 JS**（N4g 决策 j 的缺口，独立于本批）。

**一句话的边界**：N4g 之前手机只会「往库里加」，N4g 之后会「修、收、送出去」；**N4i 之后它才会「一次动很多首」与「改一首歌是从哪来的」**。

## §1 开工前必须知道的

### 1.1 桌面那张菜单有十二项，手机现在有五项

桌面 `packages/gui/src/renderer/src/components/SongRow.tsx:214-275`，手机 `apps/mobile/src/ui/songs-tab.tsx:154-174`。逐项对照与本批的去留：

| 桌面项 | 手机现状 | 本批 |
|---|---|---|
| 播放 | 行本身就是（N2f 决定） | — |
| 添加到歌单（子菜单） | **没有** | ✅ 进**批量**动作（选一首也能用），不再单独做一项行菜单 |
| 从当前列表移除 | 歌单详情的行菜单有「移出歌单」 | ✅ 扩到批量 |
| 重新下载歌词 / 删除歌词 | 没有 | ❌ 决策 f：手机上没有任何歌词管理面，两项没有落脚点 |
| 复制歌曲 ID | 没有 | ❌ 决策 f |
| **复制链接** | **没有** | ✅ 决策 d（新依赖 `expo-clipboard`） |
| **打开链接** | **没有** | ✅ 决策 e（RN 自带 `Linking`，**零新依赖**） |
| **编辑链接…** | **没有** | ✅ 本批最大的一块，§1.2 |
| 固定 / 取消固定 | 有（单首） | ✅ 扩到批量 |
| 重新下载 | 有（N4g 加的） | — |
| 删除歌曲 | 有（单首 + 确认） | ✅ 扩到批量 |
| 改歌名 / 改歌手 | 手机独有（桌面在行内直接编辑） | — |

### 1.2 「更改链接」的两段逻辑**今天只有 daemon 有**，而两段都不在 portable

这是 N4a 那件事的第二个实例（preflight「四条判断只有 daemon 有」）：

| 段 | 在哪 | 干什么 |
|---|---|---|
| 四分支归一化 | `packages/daemon/src/routes/songs.ts:169-210` `resolveSourceUrl` | 空 → 清掉整个三元组 · B 站视频链接 → **在线归一**（短链展开、`p` → `cid`）· 其它 `http(s)` → 保留 url、**不给身份**（R8）· 其它 → `INVALID_SOURCE` |
| 预览（不写库） | 同文件 `:273-303` `POST /songs/:id/recognize-url` | 短链展开 → 必须是 video → `normalizeSourceOnline` + 一次 `view` 拿标题 → 回 `{source_url, source_provider, source_key, video_title}` |

**它们用的零件全在 portable**（`parseSongInput` = `portable/download/link.ts:71`，`normalizeSourceOnline` = 同文件 `:154`，`expandShortLink` 在 client 上），**只有这两段编排在路由里**。手机要「更改链接」就必须有这两段——**照抄一份就是第三份实现**（daemon 一份、手机一份，而规则有四个分支）。决策 a 就是这件事。

🔴 **提取要按 N4a 的做法**：**先给 daemon 现有行为补 characterization 测试，再搬**，否则「零行为变化」没有判据（N4a 的原话）。`routes/songs.test.ts` 现在覆盖到哪一步要先数一遍。

### 1.3 `reidentifySource` 的账 **N4g 已经结清了**，N4h 记的那句要更正

N4h 写的是「`reidentifySource` 有实现、判据 29 验过，但生产 UI 没入口，已计入 N4i」，并说「它在桌面挂在『编辑链接…』里」。**两句都要更正**：

- 它**不是**一个按钮，桌面也不是。它在引擎里：`portable/download/engine.ts:824-841` —— `redownload` 与 `ensure-file` 两种任务在**存下来的 key 探不通**时自动调它（有 LLM 就重新找、没有就 `SOURCE_GONE` 并说怎么修）。
- 所以**入口 = 触发这两种任务的路**，而 N4g 两条都给了（行菜单「重新下载」+ 点没有文件的行）。**这条账已经关了**，本批不重复做。
- 桌面「编辑链接…」里的「自动识别」是**另一件事**（`recognize-url`：拿用户输入的 URL 去归一并预览标题，不用 LLM）。本批做的是这一个。

### 1.4 选择模型已经有一个，而且是泛型的

`apps/mobile/src/downloads/selection.ts:94-129`（N4f 写给选择页的）：`chooseAll` / `toggleOne` / `toggleEvery` / `allChosen` / `chosenRows`，全部只要求行有一个 `key: string`（`Pickable`，`:25`）。**歌曲行用 `song.id` 当 key 就能直接复用**——本批**不写第二个勾选模型**，只在需要时把它挪到一个中立的位置（决策 g 的一部分）。

### 1.5 新依赖只有一个，而「打开链接」根本不需要依赖

- **复制链接**要 `expo-clipboard`（RN 核心的 `Clipboard` 早已移除）。**新依赖 ⇒ 常驻规矩②：`pnpm install` 变动后复跑桌面 `just check` + `just test`**，且原生模块 ⇒ 必然要重建 APK。
- **打开链接**用 **React Native 自带的 `Linking.openURL`**，零依赖（`expo-linking` 虽然在依赖里，但那是分享 intent 插件带的，不是这条路要的）。

### 1.6 `BackHandler` 在这个应用里是第一次用

全仓 `apps/mobile/src` 现在**一次都没有** `BackHandler`（实测 grep 为空）。选择模式必须能用系统返回键退出——否则手机上唯一的退出方式是找到那个 ✕，而这是 Android 用户第一个会按的键。**它是全局的**：注册在选择模式打开时、注销在关闭时，返回 `true` 表示「我吃掉了这次返回」。⚠️ 与已有的两个 Modal（全屏播放页、队列面板）叠加时的优先级要在真机上确认一次（判据里有）。

### 1.7 选择模式改变了「点一行」的意思，这是本批唯一的语义冲突

平时点一行 = 播放（N4g 之后还包括「没有文件就去拿」）。选择模式里点一行 = 勾选。两种意思共用一个手势，所以**进入方式必须是长按**（决策 b），且**屏幕上必须一眼看得出在哪个模式**（顶栏变成「已选 N 首」+ 动作）。minibar 与播放**不停**（决策 g）。

### 2.2 选择模式的状态机

```
        长按一行
浏览 ─────────────→ 选择（chosen: Set<songId>，至少 1）
 ↑                      │ 点行 = 勾/去勾 · 全选 · 计数
 │                      │
 └──── BackHandler / ✕ / 动作完成 ────┘
```

- **动作完成即退出**（照桌面：批量做完清空选择），失败也退出但把结果说清楚。
- **播放不受影响**：minibar 照常，正在播的行照常高亮。
- **切 tab 会不会保留选择**：不保留（tab 是条件挂载的，状态本来就没了）——如实写进判据。

### 2.3 批量动作的执行口径（照 N4f 的「准入 / 执行」措辞）

| 动作 | 怎么执行 | 部分失败怎么说 |
|---|---|---|
| 固定 / 取消固定 | 逐条 `pinSong`（同步） | 逐条都不会失败（除非行没了）；只报「已固定 N 首」 |
| 加入歌单 | **一次** `addPlaylistSongs(id, songIds)`（core 已支持数组） | 已在歌单里的不重复加（core 的语义），只报最终数 |
| 删除 | **逐条** `deleteSong`（每条都要 drain 文件 journal，core 没有批量删） | 「删了 N 首，M 首没删成」+ 日志；**不中断** |
| 移出歌单 | 逐条 `removePlaylistSong` | 同上 |

🔴 **删除是本批唯一「逐条 await」的动作**，十首歌就是十次 drain。UI 必须显示进行中（禁用按钮 + 计数），否则看起来卡住。

### 2.4 更改链接页

```
当前链接（可清空）
      ↓ 自动识别（不写库）
预览：视频标题 + 归一后的 source_key
      ↓ 保存
四分支之一 → updateSong({source_url, source_provider, source_key})
      ↓（key 变了且这首歌有文件）
提示「要不要重新下载」→ 是 = enqueueRedownload
```

- **桌面还有一个 409 冲突分支**（新链接已经属于另一首歌）：桌面会把那首歌找出来给你看。手机上**只说清楚是哪一首**（名字），不做跳转（决策 h）。

## §4 判据（接着 N4g，从 53 起）

53. **【gate · 上机】选择模式的进出**：长按一行进入 → 顶栏显示「已选 1 首」→ 再点两行 = 3 首 → **系统返回键退出**（不是退出应用、不是退到上一个 tab）→ 再长按仍能进。**全选**把当前这一屏（含搜索/排序结果）全勾上。
54. **【上机】批量固定**：选 3 首 → 固定 → 三行都出现图钉；再选同样 3 首 → 取消固定 → 图钉都没了。**混合选择**（2 首已固定 + 1 首没有）时两个动作都是幂等的。
55. **【上机】批量加入歌单**：选 3 首 → 加入某歌单 → 歌单里正好多这 3 首；**其中一首本来就在里面时不重复**。
56. **【gate · 上机】批量删除**：选 3 首 → 确认 → 三行消失，**设置页的「曲库目录」数正好少 3**（文件真的没了，不是只删了行）。执行中按钮禁用且有计数。
57. **【上机】歌单详情里的移出歌单**：选 2 首 → 移出 → 歌单里没了、**歌曲 tab 里还在**（这条是「移出 ≠ 删除」的唯一证据）。
58. **【单测 + 上机】复制链接 / 用 app 打开**：有链接的行两项可用（复制后粘到添加页能识别；打开跳到浏览器或 B 站 app）· **没有链接的行两项灰掉** · **`source_url` 不是 http(s) 时拒绝打开**（单测覆盖判定函数）。
59. **【gate · 上机】更改链接四分支**：① 清空 → 三元组全空，行上出现「需要下载」也不再能重新下载（说得出为什么）· ② 一条 B 站视频链接 → 自动识别显示视频标题 → 保存后 `source_key` 是 `bvid:cid` 形态 · ③ 一条别的 `http(s)` 链接 → 保留、可打开、**不能下载** · ④ 一段乱码 → 拒绝并说支持什么。**短链要能展开**（`b23.tv`）。
60. **【单测】提取零行为变化**：`resolveSourceUrl` / `recognizeUrl` 的 characterization 测试**先写在 daemon 上**（覆盖四分支 + 短链 + 非视频链接 + 409 冲突），提取之后**一个字不改地全绿**；再加 portable 侧的直接单测。**反测**：把「其它 http(s) 保留」改成拒绝 → 必须红。
61. **【上机】选择模式不打架**：选择模式下 minibar 还能播/暂停/切歌 · 点行**不播放** · 打开全屏播放页再返回，选择模式**还在**（或明确说明不在——两者都可以，但要与实现一致）。
62. **【上机】更改链接之后能重新下载**：把一首歌的链接改成另一个真实视频 → 提示重新下载 → 下完之后**播的是新视频的音频**（时长对得上）。

## §5 决策（a–h，**待用户关闭**）

| # | 决策 | 倾向 | 理由 / 代价 |
|---|---|---|---|
| **a** | 「更改链接」的四分支归一化怎么办 | **提取进 `portable/download/source-url.ts`**，daemon 变薄壳，**先补 characterization 再搬** | 照 N4a 的 preflight 先例：一条规则两份实现必漂，而这条有四个分支 + 短链 + 在线归一。**代价**：本批多一个纯桌面批（N4i-1），且要先给 daemon 补测试。**替代方案**（手机上收窄成「只收 B 站视频链接」）会让手机与桌面对同一个输入给不同答案——正是 M6 那类分叉 |
| **b** | 选择模式的入口 | **长按进入**（不做顶栏的「选择」按钮） | 手机惯例；点/长按是两个手势，不会互相误触。**代价**：长按是不可见的入口——第一次用的人要靠猜。缓解：空库/首次可以在计数行提示一次（不做也接受） |
| **c** | 批量动作集 | **四个**：固定 / 取消固定 · 加入歌单 · 删除 ·（歌单详情）移出歌单 | 桌面还有「重新下载」「歌词两项」。重新下载批量 = 一次点出十几个下载任务，**在手机上是流量事故**（决策 d 的流量提示又不做）；歌词两项没有落脚点（§1.1） |
| **d** | 复制链接 | **做，装 `expo-clipboard`** | 把一首歌发给别人的最短路径就是复制它的链接；手机上没有第二条路（桌面还能开控制台）。**代价**：新原生依赖 + 一次桌面回归复跑 |
| **e** | 打开链接的放行范围 | **只放行 `http(s)`**，其它一律拒绝并说明 | `Linking.openURL` 会把 `intent://`、`file://` 之类交给系统——那是拿一个「用户数据里的字符串」当命令用。这是 R10 在链接上的等价物。**零新依赖**（RN 自带 `Linking`） |
| **f** | 复制歌曲 ID / 歌词两项 | **不做** | ID 在手机上没有消费者（没有控制台、没有 CLI）；歌词管理要先有一个歌词管理面。两项都留给「有人真的需要」的那天 |
| **g** | 选择模式与播放的关系 | **互不干涉**：minibar 照常、选择模式下点行只勾选、动作完成即退出选择 | 一个正在放歌的应用不该因为你要删三首歌就停下来。**代价**：屏幕上同时有两个「当前」（正在播的行 + 勾选的行），靠颜色区分（琥珀 = 正在播，勾 = 选中） |
| **h** | 更改链接撞了别的歌（409） | **只说是哪一首**（名字 + 「已经用了这个链接」），不做跳转 | 桌面会切库、清搜索、滚动定位（`EditLinkDialog.tsx:44-64`）——那是三步导航，手机上要多做一个「跳到那首歌」的通道。**代价**：用户得自己去搜那个名字 |

## §6 风险

| 风险 | 缓解 |
|---|---|
| 🔴 **批量删除逐条 drain，十首就是十次文件操作** | §2.3 写明：执行中禁用 + 计数；判据 56 要求「曲库目录数正好少 3」，即文件真的删了 |
| 🔴 **提取改了 daemon 的行为而没人发现** | 判据 60 的 characterization **先写后搬**，且带一条反测 |
| **`BackHandler` 与两个 Modal 抢返回键** | 判据 53 + 61 各验一次；实现上选择模式的注册要在 Modal 之下（Modal 有自己的 `onRequestClose`） |
| **长按是不可见入口** | 决策 b 认下这个代价；判据 53 只验它能用 |
| **`expo-clipboard` 装完桌面回归** | 常驻规矩②，N4i-2 的收尾步骤 |
