## 2 · 取证结论：锁屏播完不续播（⑪）

**2026-08-26 真机会话**，冻结设备 vivo V2408A / Android 15，release 构建 + 临时探针（探针已还原，未提交）。播「如约而至」（5:28），拨到接近结尾，`keyevent 26` 熄屏，让它自然播完。

| 探针 | 设备时刻 (ms) | 说明 |
|---|---|---|
| `ended`（`didJustFinish` 到达 JS） | 1787753102988 | 熄屏后 18.2s，**原生事件照常送达 JS** |
| `advance:ended:play` | 1787753103043 | +55ms，`decideNext` **判定正确**，选中下一首 |
| `destroy:enter` → `destroy:paused` | 103059 → **103060** | +1ms，`driver.pause()` 执行了——**这就是「自动暂停」** |
| `destroy:settled`（`await sleep(300)` 之后） | **1787753166597** | **+63 537ms** |
| `destroy:removed` → `play:started` | 166600 → **166679** | 解冻后 **82ms** 全部走完 |

**根因**：`apps/mobile/src/player/driver.ts` 的 `await sleep(PAUSE_SETTLE_MS)`（一个 JS `setTimeout`）是自动续播链路上**唯一**一个依赖 JS 定时器的步骤，而熄屏时 JS 定时器被冻结。300ms 走了 63.5 秒。

两条比 `LESSONS.md` 现有记录更锋利的事实：

1. **放开冻结的不是「屏幕亮」，是「Activity 回到前台」。** 1787753157238 唤醒屏幕，到 158922 连采 24 次仍是 `STOPPED(1) position=328031`；直到用户**解锁**才走完。
2. **「听状态流等暂停生效」这条路走不通**（曾是候选修法）：`BaseAudioPlayer.kt:84` 在 `STATE_ENDED` 下把 pause 的状态更新当 transient 吞掉——**正好就是播完这个场景**。

**修法**：`modules/lark-app` 加一个原生 `delay(ms)`，播放链路上不再有 JS 定时器。不动那条冻结的拆卸顺序（pause → settle → clear → remove），因为它防的是 expo/expo#47569 的 AudioTrack 泄漏，熄屏时同样成立。

## 3 · 分批

> 每批 = 一次提交。判据一律要能说出**它怎么变红**。手机端新增的判定**必须落在 Node 能加载的模块里**并加进 `apps/mobile/vitest.config.ts` 的白名单——那个 include 是显式列表，不加等于没测（`INVARIANTS.md` §7 最后一条）。

### P1 · 界面账（② ③ ④ ⑩ ⑫）

**改什么**
- ② `App.tsx` 删掉 24px 的 `lark` 标题；`paddingTop: RNStatusBar.currentHeight` 原样保留，内容首行补 8px。打不开曲库/正在打开两个状态页自带一句话，不再依赖那行标题。
- ③ `add-tab.tsx` 整页收成**一个 `FlatList`**，输入框那一坨 + 任务列表表头当 `ListHeaderComponent`（不能用 `ScrollView` 套 `FlatList`）。🔴 header 必须传**稳定元素**，否则每敲一个字输入框失焦。
- ④ 新增 `src/ui/back.ts`：一个模块级返回处理器栈，组件挂载时 push、卸载时 pop，`BackHandler` 从栈顶往下问，全部答 false 才交给系统。**不调 `exitApp()`**（`INVARIANTS.md` §6：它只 finish Activity）。四级：多选 → 歌单详情 → 非「歌曲」tab → 系统。其余浮层已经是 `Modal`，`onRequestClose` 早就接住了返回键，**不动**。
- ⑩ 抽 `src/library/song-actions.ts`（**纯函数**，返回菜单条目列表）+ `src/ui/song-actions.tsx`（渲染）。歌曲 tab 与歌单详情共用，歌单上下文多一条「移出歌单」。顺带让 `playlists-tab.tsx`（592 行）回到 500 行以下。
- ⑫ `settings-tab.tsx` 删 曲库目录 / schema / protocol / 启动判定 / install_id / device_uuid / 启动时执行的文件操作 / 蓝牙歌词发送（本首）；留「曲库 N 首」与「最近的错误」（后者默认折叠）。

**判据**
- `back.test.ts`：注册顺序、答 false 继续下传、卸载后不再被问。**破法**：把栈改成只问最后注册的一个 → 红。
- `song-actions.test.ts`：曲库上下文九项、歌单上下文十项且含「移出歌单」。**破法**：歌单上下文漏传 → 红。
- ②③ 的留白与滚动**只有设备能答**，进 P7 的真机会话。

**风险**：③ 的 header 失焦是这批唯一会「看起来对、用起来错」的地方，真机会话要专门敲一次字。

### P2 · 锁屏续播（⑪）

**改什么**
- `modules/lark-app` 加 `AsyncFunction("delay")`（Kotlin 侧 `kotlinx.coroutines.delay`）。
- 新增 `src/ports/delay.ts`：`delay(ms)` 端口，真实实现走原生模块。
- `driver.ts` 的 `sleep` 改用它，删掉本地那个 `setTimeout` 版本。

**判据**
- 新守卫 `check-mobile-no-js-timers.sh` 进 `just check`：`apps/mobile/src/player/` 下不许出现 `setTimeout` / `setInterval`。**破法**：把 `sleep` 换回 `setTimeout` → 红。（这是这条修复唯一能在电脑上变红的判据——`driver.ts` 自己 import expo-audio，进不了 vitest 白名单。）
- 现有 `check-mobile-native-modules.sh` 自动覆盖新方法的接线（`.kt` / `android/build.gradle` / `index.ts` 三件套）。
- 真机（P7）：熄屏播完一首，**3 秒内**续播且通知栏标题换成下一首。**现状是 63 秒且要解锁**，所以这条判据现在必红。

**风险**：改原生模块 `pnpm patch` 没用，要靠 `expo.autolinking.buildFromSource`（已配）。

### P3 · 下载记录持久化（⑦ + ⑨ 的界面）

**改什么**
- 新增 `src/downloads/history.ts`（**纯**，`load`/`save` 注入，照 `ports/device-settings.ts` 的形状）：终态任务落盘，**每个曲库一份**，路径由 `ports/paths.ts` 出口（工作区收口守卫要求）。
- 每条记录带**重下所需的一切**：`DownloadTarget`（bvid/page/naming 或 keyword）、`playlistIds`、`url`、失败码与失败原因、尝试次数。
- 记录**不自动删**，但有条数上限（**拟 200**，见 §5）。
- 界面：任务列表下面接「下载记录」，每条可**删除**、可**重下**；表头两个按钮——**清空记录** 与 **全部重试**（只重试失败的那些）。
- 重下：失败记录 → `enqueueDownload({target, playlistIds, url})`；已成功的歌还在 → `enqueueRedownload(songId)`。

**判据**
- `history.test.ts`：写入/读回/裁剪到上限/**文件损坏当空读且不删原文件**（照 `device-settings` 的口径）。**破法**：让损坏分支覆盖写 → 红。
- `history.test.ts`：一条失败记录能还原出与原请求等价的 `EnqueueDownloadInput`。**破法**：漏存 `page` 或 `naming` → 红。
- 真机（P7）：**杀进程再打开，记录还在**。

**风险**：🔴 **不进 `songs.db`**。schema v3 是两端共用的，加表 = 一次 schema 迁移 + 桌面跟进，这一版不动库。

### P4 · 自动重试（⑧）

**改什么**
- 新增 `src/downloads/retry.ts`（**纯**）：`shouldRetry(code, attempts, limit)`。
- 装配根订阅 hub 快照，命中就重新入队，并把新旧任务在记录里串成一条（`attempts` 累加）。
- 设置页加「下载失败自动重试」：0/1/2/3 次（**默认 1**，见 §5）。

**判据**
- `retry.test.ts`：网络类 → 重试；`INVALID_SOURCE` / `AUDIO_NOT_AAC` / `LLM_NOT_CONFIGURED` / `DOWNLOAD_QUEUE_FULL` / `BILIBILI_RISK_CONTROL` / `SOURCE_GONE` → 不重试；到次数 → 不重试。**破法**：把风控也算进网络类 → 红。

**风险 🔴（动工第一件事要查清）**：**「网络失败」在这个引擎里到底以什么 code 出现。** `describeTaskError` 的兜底把认不出的一律记成 `INTERNAL_ERROR`，而**手机上最常见的失败——传输超时——很可能正落在兜底里**。若如此，「只重试网络类」会漏掉最该重试的那一类，等于什么也没做。落地前要先把传输超时/连接失败各造一条，看它们的真实 code；必要时给传输失败一个自己的码。

### P5 · 缓存上限门 + 歌单全部下载（⑤）

**改什么**
- 新增 `src/downloads/budget.ts`（**纯**）：给定「已用字节 + 已排队的估算 + 上限」，答下一首**能不能排**。估算用时长 × 平均码率（时长库里有）。上限 0 = 不限 ⇒ 一律能排。
- 歌单详情操作栏加「**全部下载**」：只排 `has_file === false` 且有来源的（imported 没有 `source_key`，下不了）。撞到上限就**停止排队**，剩下的每首写一条失败记录，码 `CACHE_LIMIT`，话说明白：调高上限，或手动重试（手动重试**绕过**这道门，即接受下新删旧）。
- 手动路径（点一首歌、菜单里的重新下载、记录里的重下）**不受这道门约束**——门只管自动路径。

**判据**
- `budget.test.ts`：贴着上限时下一首排不进；上限 0 时全排；估算把已排队的算进去（否则一次全排进去再一起超）。**破法**：只看已用不看已排队 → 红。
- `history` 侧：`CACHE_LIMIT` 的失败记录可重试，且重试走的是**绕过门**的路径。**破法**：重试也过门 → 永远重试不成功 → 红。
- 补 `INVARIANTS.md` 已有那条的判据：一首**排队中**的歌不会被清理挑走（`services/library.test.ts` 的 `createCacheOptions` 已有排除源测试，补一条排队态的）。**破法**：把 `pendingFileSongIds` 从排除源里拿掉 → 红。

### P6 · 自动下一首下载 + 预缓存（⑥，含桌面）

**改什么**
- `packages/shared/src/play-queue.ts`：`decideNext` 加一个**必传**的开关（不是可选带默认值——默认值会造成「忘了传」的静默分叉）。开着时 `ended` 不再跳过没有文件的歌。
- 手机：设置页加开关（**默认开**），存 device settings。
- 手机预缓存：当前歌起播时看队列**下一首**，没有文件就 `engine.enqueueEnsureFile`。🔴 **不走 `ensureController`**——那是「一个槽位、最后一次点击赢」的**播放意图**，占了它会抢播。预缓存也过 P5 的上限门。
- 只在**顺序 / 列表循环**下预缓存：`shuffle` 的下一首是随机的，预缓存无从谈起；`repeat-one` 不需要。
- 播完时下一首还没下完 → 走现在「点一首没文件的歌」那条路（等下完再播），即用户描述的行为。
- 桌面：`stores/player.ts` 的 `ensureFile: trigger !== 'ended'` 跟着开关走，设置页加同一个开关（新 config 字段）。

**判据**
- `play-queue.test.ts`：同一个队列、同一首没有文件的歌，开关两态给出**不同**判定。**破法**：把参数忽略 → 红。
- `store.test.ts`：起播时按队列下一首发出预缓存请求；shuffle 下不发；**预缓存不占播放意图**（发完之后一次用户点击仍然能抢到）。**破法**：预缓存走 ensureController → 抢播测试红。

**风险**：桌面动了 ⇒ 发桌面版时要复跑五套 accept（本版不发桌面，这笔账记到 backlog D1）。

## 4 · 已知取舍

- **下载记录不进数据库**，因此**不同步**、不跟着账号走：它是这台设备这份曲库的下载史。
- **预缓存会在没人看着的时候用流量**。「只在 Wi-Fi 下预缓存」要引入 `expo-network`，**这一版不做**；开关本身可以关掉整件事。
- **自动重试不做退避排程**：熄屏时 JS 定时器冻结，一个「30 秒后重试」的定时器在锁屏后就是假死。重试**立即重新入队**，次数用完为止。
- **`shuffle` 不预缓存**，播完随机到没有文件的那首仍然要等下载。

## 5 · 动工前要答的（我给了建议值，按默认走也行）

1. **下载记录保留多少条**？建议 **200**，超了从最旧的丢。
2. **自动重试默认几次**？建议 **1**（选项 0/1/2/3）。
3. **桌面要不要也做预缓存**？建议**先不做**，桌面这一版只跟「自然播完也去下载」的规则和开关；理由是桌面改动越多，下一个桌面版的 accept 复跑面越大。
4. **「全部下载」要不要在歌单列表页也放一个**？已定在详情页操作栏；列表页**不放**（否则一个误触就是几十首）。

## 6 · 依赖顺序

```
P1 界面 ─┐
P2 锁屏 ─┼─ 互不依赖，可并行
P3 记录 ─┘         ↓
            P4 自动重试（要记录里的 attempts）
            P5 上限门 + 全部下载（要记录承载「到上限」的失败）
                    ↓
            P6 自动下一首 + 预缓存（要上限门）
                    ↓
                  P7 发版
```
