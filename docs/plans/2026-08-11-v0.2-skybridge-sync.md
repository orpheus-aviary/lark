### 3.1 实体与 op **(R4-2 修订：membership create 去 rank)**

LWW put 为全量状态；`created_at_ms`/`added_at_ms` **不可变**（insert 采用，update-existing 忽略）。⚡ metadata-op 不含 LWW 戳、按 `server_seq` 定序、**回放自己的回声**。

| entity_type | entity_id | op | payload | 类型 |
|---|---|---|---|---|
| `song` | song uuid | `create`/`update` | `{name, artist, source_url, source_provider, source_key, lyrics_offset, duration, created_at_ms, updated_at_ms, lww_counter}` | LWW put |
| | | `delete` | `{updated_at_ms, lww_counter}` | 墓碑 |
| | | `set_lyrics` `{lrc}` / `clear_lyrics` `{}` | | ⚡ |
| `playlist` | playlist uuid | `create`/`update` | `{name, created_at_ms, updated_at_ms, lww_counter}` | LWW put |
| | | `delete` | `{updated_at_ms, lww_counter}` | 墓碑 |
| | | `reorder` | `{song_ids: [uuid…]}` | ⚡ |
| `playlist_song` | `` `${playlist_id}:${song_id}` `` | `create` | `{playlist_id, song_id, added_at_ms, updated_at_ms, lww_counter}`——**不含 rank** | LWW put |
| | | `delete` | `{updated_at_ms, lww_counter}` | 墓碑（可复活） |
| | | `set_rank` | `{rank}` | ⚡ |

**rank 单通道（R4-2 收口）**：membership 的 LWW put **完全不携带 rank**（四版「仅 insert 采用」与复活条款互相冲突、且 create 回声被 self-replay 跳过而其他设备采用 payload rank，仍是第二条通道——评审场景：A 添加成员 X 按本机尾部得 rank，B 的 reorder 先取得 seq，A pull 后 X 被改写、再 push create，A 跳过自己回声而其他设备采用原 rank，分叉）。冻结为：
- **每次 add / 复活 = 成对 emit `create` + `set_rank`**（同事务、连续 local_seq，回放序天然 create 在前）；create 只管存在性与 `added_at`，**最终 rank 一律由可自回放的 `set_rank` 决定**。
- create 的 apply 三分支见 §3.2（R5-1）；缺行/复活插入时的**临时安置 rank = 本地该歌单 max(rank)+1024**（空单 1024），只是 set_rank 到达前的短暂过渡，终态由 set_rank 统一。
- **回填同样成对生成**（§3.7：每条 membership 行 emit create + set_rank）。

payload 校验器（同前版）：字段全必填（nullable 仅 `source_*`）；`(provider IS NULL)=(key IS NULL)`；provider 白名单/key 格式复用 `normalizeSource`；字符串上限下沉 `shared/limits.ts`；时间戳/counter safe integer；`duration ≥ 0`、`lyrics_offset`/`rank` 有限 real；`song_ids` 元素 uuid。失败 → §3.8。

### 3.2 墓碑 + 父墓碑门

**`sync_tombstones`（0002）**：`(entity_type, entity_id, updated_at, lww_counter, device_id /*nullable，比较时 NULL≡''*/, deleted_at, PRIMARY KEY(entity_type, entity_id))`。本地删除与 apply 远端删除都写墓碑；retention 只清 `sync_changes`。

- **song / playlist：delete 永久胜出**；**playlist_song：LWW 复活**。统一判据：先对 `max(行, 墓碑)` 比较（song/playlist 墓碑视为无穷大）；update-on-missing 且无墓碑 = insert。
- **(R5-1) membership create 的 apply 三分支冻结**（两设备并发添加同一成员时接收端已有存活行，LWW 状态必须收敛，否则介于两者之间的 delete 会一端生效一端失败）：
  1. **存活行且 create > 行**：**只更新 LWW 三元组**（`updated_at/lww_counter/device_id`），保留本地 `added_at` 与 rank；
  2. **缺行、或 create > 墓碑（复活）**：插入，采用 incoming `added_at`，临时安置 rank（§3.1），清墓碑；
  3. **create ≤ max(行, 墓碑)**：skip；输给墓碑时其**配对 set_rank 由 §3.5 的「行存在门」自然拦截**。
- **父墓碑门**：`set_lyrics`/`clear_lyrics` 在 song 墓碑/缺行时 skip；`reorder` 在 playlist 墓碑/缺行时 skip；membership `create`/`set_rank` 在任一父墓碑/缺行时 skip。**判定次序：父墓碑门 → ⚡ 回声分支 → self-replay → LWW**（门在回声之上，自己的回声同样被拦）。
- 级联：song/playlist delete 同事务 cascade 删成员行（不写成员墓碑不 emit）；文件处置走 §3.6。

### 3.3 HLC + 注册 rebase（R32-②）

- 比较键 `(updated_at_ms, lww_counter, device_id)` 严格字典序；NULL device 归一 `''`；平手保本地。HLC-lite 照 owl。
- **rebase 只在 binding 首次写入的注册事务内执行一次**，前置不变量「每个存活实体 ≥1 条 pending LWW op」由同事务先行的运行期回填保证（§3.7）：
  1. 逐实体重排：凡实体的 {行、墓碑、pending payload} 任一键 ms > `server_now + 5min`，其全部 pending LWW op 按 `local_seq` 重排为 `(server_now, 0..k)`，行/墓碑三元组 := 末条 op 的新键。
  2. 墓碑随其 pending delete 一起重排；⚡ 无键不重排（`json_type(payload,'$.updated_at_ms')='integer'` 为门）。
  3. HLC seed = rebase 后全部本地 LWW 状态（行 + 墓碑 + pending payload）的最大键。

### 3.4 同 provider key 并发：共存 + 可见提示（R32-① 修订，**D8 已拍板**）

- 0002 把 `idx_songs_source_key` UNIQUE 降为普通索引；CHECK 不动。本地防线不变，重复只可能由 sync 注入。apply 无碰撞路径，按构造收敛。
- 可见性：`/sync/status` 与 GUI popover 报 `duplicate_source_keys`；列表同 key 组标「重复」；`lark songs --duplicates`。手动删一首即清理。
- 代码影响面（冻结）：`assertKeyFree` 改「key 未变不查、变更为其他存活行已持有仍拒」；`findSongByKey` → `findSongsByKey`，n>1 → `AMBIGUOUS_SOURCE_KEY`（绝不任挑）；下载复用/歌单导入/link 编辑/缓存探活四处审计 + 测试。
- 未来合并 = 用户显式指令（走既有 op），v0.2.x+。

### 3.5 rank：全 server_seq 语义（R32-③）

- 单曲拖拽：本地写 rank（不碰 LWW）+ emit `set_rank {rank}` ⚡。add/复活：**create + set_rank 成对**（§3.1）。
- 归一化：本地 rank-only 重铺（`rank.ts:29` 必改）+ emit playlist `reorder {song_ids}` ⚡。
- apply：`reorder` song_ids 去重（保首现）→ **仅对本地存在的列表内成员**按序 `rank=(i+1)*1024`（列表内缺行者忽略），列表外本地成员保相对序追加尾部；`set_rank` 直接写。两者过父墓碑门、回放回声、不碰 LWW。**`set_rank` 的门 = 父墓碑门 + membership 行当前存在**（缺行 skip——同时充当输给墓碑的 create 的配对拦截，R5-1③）。
- `REORDER_SYNC_MAX = 4000`：超限归一化退化为逐行 `set_rank` ⚡ + warn；reorder 绝不 local-only。

### 3.6 file-effect journal + FileEffectRuntime **(R4-3 / R4-P1-1 修订)**

```sql
CREATE TABLE sync_file_ops (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  kind          TEXT NOT NULL,
  song_id       TEXT NOT NULL,
  arg           TEXT,              -- JSON，含入队前生成的 op_uuid；快照齐全
  created_at    INTEGER NOT NULL,
  attempts      INTEGER NOT NULL DEFAULT 0,
  last_error    TEXT,
  next_retry_at INTEGER
);
```

**歧义澄清（评审）**：journal 表**不加 uuid 列**——`op_uuid` 在入队前生成、写进 arg JSON；`quarantine_target = recovered-songs/<song_id>-<op_uuid>/` 由它派生，入队时定死。

| kind | arg（入队事务内快照） | 语义（幂等） |
|---|---|---|
| `delete_song_files` | `{op_uuid, policy:'local'}` | 整目录删（本机已确认） |
| `delete_song_files` | `{op_uuid, policy:'remote', audio_origin:'imported'|'downloaded'|null, lyrics_disposition:'delete'|'quarantine', quarantine_target}` | **(R4-3)** `audio_origin` 从行上快照：downloaded 删、imported 隔离、**null（未知）默认「有文件则隔离」**；**歌词处置在入队事务内判定**：该 song 存在 pending `set_lyrics`/`clear_lyrics`（`synced_at IS NULL`）**或**歌词 outbound dead-letter → `'quarantine'`，否则 `'delete'`——**executor 不做任何大小/同步状态推断**（四版「≤240KB 即已同步」不成立：pull-first 窗口里本地小型 pending 歌词会被误删，唯一副本丢失） |
| `quarantine_song_files` | `{op_uuid, quarantine_target}` | 移入目标；复跑按「目标已存在」识别完成 |
| `write_lyrics` | `{op_uuid, inline?: lrc(≤256KB), staging?: {path, sha256}}` | 覆盖写；staging 验哈希后 move |
| `delete_lyrics` | `{op_uuid}` | 删缺失 = 成功 |

- 失败状态机：同 song_id 严格 FIFO、异歌可越过 busy/失败行；失败 `attempts+1` + 退避 `next_retry_at`；`attempts ≥ 5` 停自动重试、进 `/sync/status.file_op_failures`。
- **(R4-P1-1) 产品内恢复（v0.2 就有，不留 v0.2.x）**：`POST /sync/file-ops/retry {id?}`（缺省全部失败行）重置 attempts/next_retry_at 立即重跑；**「确认跳过」是独立危险操作** `POST /sync/file-ops/discard {id}`——删 journal 行前先把 arg 摘要记入 dead-letter(out, reason `file_op_discarded`) 留审计，CLI/GUI 均需显式确认。unbind 的 drain 前置由 retry/discard 解锁。
- **(R5-P1-1) 发现通路与并发规则**：新增 **`GET /sync/file-ops?state=failed|pending`** 返回脱敏摘要（id/kind/song_id/attempts/last_error/next_retry_at/created_at；arg 里的 inline 歌词正文替换为 `{size, sha256}`，**绝不返回正文**）——retry/discard 需要的 id 由此获得。**retry / discard / drain 共用 FileEffectRuntime 的执行互斥**；discard 仅允许「永久失败（attempts ≥ 5）且非执行中」的行，否则 409 `FILE_OP_BUSY`——杜绝一边执行文件操作、一边把该行记成 discarded。CLI：`lark sync file-ops`（无参数 = 列表）`[--retry [id]|--discard <id>]`（discard 走全局 `--yes` + 打印将放弃内容）。
- `FileEffectRuntime` 接口冻结：daemon 注入 claim 挂接；调用方已持 claim 传入复用；后台 drain / `--direct` / boot 自取。
- boot 顺序：writer 锁 → 开库 → 先 drain journal → `recoverSongsStore`（跳过 pending journal 引用目录）。
- 超大歌词不进 DB：inline 上限 256KB，更大走 staging + sha256（boot 按龄清孤儿）。
- cursor 推进在 apply 批事务内。执行时机：daemon 相关写路由/每批 apply 后 await + boot drain；`--direct` 退出前 drain。
- 重构清单（T1）：`deleteSong` → tx{删行 + cascade + emit + 墓碑 + journal(policy:'local')}；apply 墓碑 → 同 tx journal(policy:'remote'，快照 origin + lyrics_disposition)；`writeLyrics/deleteLyrics` 接 db/sqlite。`landSongFile` 补偿通道独立不动。

### 3.7 binding / 登录 / 回填 / unbind **(R4-1 / R4-P1-2 修订)**

- **binding 单例表**（0002）：`sync_binding (id INTEGER PRIMARY KEY CHECK (id=1), server_id, user_id, workspace_id, schema_version, bound_at)`；首次登录注册事务内 INSERT，不可变；后续登录全匹配预检，不符 → `SYNC_BINDING_MISMATCH`。
- `sync_cursor`（0002 重建）：`(server_id, workspace_id, pulled_seq, pushed_seq, updated_at, PRIMARY KEY(server_id, workspace_id))`，upsert 绑定参数。
- schema 门：采认 workspace 后校验 `schema_version === 1`。HTTPS 强制 + `allow_insecure_http` 跳闸随 login 请求携带（GUI/CLI 双确认），成功后落 toml。
- **(R4-1) 回填整体运行期化（含歌词）**：0002 **不再做 SQL 回填**，只初始化 `sync_backfill_done_generation = 0`、`sync_backfill_target_generation = 1`。登录安装事务内 `done < target` 时运行 `runFullBackfill`：
  1. create-op 回填（SQL 例程）：songs → playlists → **playlist_songs（每行成对 create + set_rank，R4-2）**；payload 全量；cid = 合法 UUIDv4；`NOT EXISTS(op='create')` 防与真实 emit 重复。
  2. **歌词回填**：扫描各 song 的 `lyrics.lrc`（fs 预读在事务外完成，emit 在事务内），逐首 emit `set_lyrics`（local_seq 自然排在其 song create 之后）；序列化超 240KB → outbound dead-letter（摘要）。**v0.1 存量歌词、migrate-go 迁移歌词、unbind→重登由同一条路径覆盖**——四版里这三处都拿不到 set_lyrics，新设备永远缺歌词。**(R5-2) stale 防护**：事务内每首 emit 前复查——该 song 已有 pending `set_lyrics`/`clear_lyrics`（`synced_at IS NULL`）或歌词 outbound dead-letter → **丢弃预读快照、跳过 emit**（更新内容已由该 pending op 携带）；检查与 emit 在同一 immediate 事务内，SQLite 写锁保证与歌词任务的写入无缝隙——堵住「预读 L1 → 歌词任务写 L2 并 emit → 回填以更高 local_seq 把 L1 写回全网」的覆盖窗口。
  3. 置 `done = target`。
  **migrate-go 特判删除**：临时库建在 v2 上，generation 天然 0<1，迁移后的首次登录统一回填（含歌词）；migrate-go 不再调用回填、不再 bump generation。unbind：`target += 1`。
- **登录安装序列（顺序冻结）**：login → 取 `server_id`（无则拒）→ binding 预检 → `registerDevice`（优先复用存量 ID；吊销/不存在才新注册）→ 重建带 deviceId 的 client → `ensureWorkspace` → schema 门 →（同一事务：）binding 写入（首次）→ **① `done < target` → `runFullBackfill` ② rebase（§3.3）③ device_id 回填/重打戳 ④ `done = target` ⑤ retention watermark** → 写 toml → 装 session → 起 handles。**执行条件写死（R5 歧义澄清）**：① 只看 generation；② **仅当本事务写入了 binding（首绑或 unbind 后重绑）才执行**；binding 既存且 generation 已平的普通重登，①②③④ 全部跳过。
- **(R4-P1-2 / R5-P1-2) 全程统一补偿**：安装序列**任一阶段**失败（binding 预检 / registerDevice / ensureWorkspace / schema 门 / DB 事务 / 写 toml / 装 session 与起 handles）→ 补偿**顺序冻结：先 best-effort revoke（仅当本轮新注册了设备；复用的存量设备绝不 revoke）→ 后 best-effort 远端 logout**——logout 会作废整个 token family，反序将无凭证可执行 revoke（owl `sync-auth-transport.ts:210` 同款）。**toml 回滚**：写 toml 前暂存旧文件（原不存在则记为「无」）；后续装 session / 起 handles 失败 → 还原旧 toml 或删除新写文件——磁盘不留已 logout 的死 token。
- device_id 回填/重打戳：首次注册：三表 + 墓碑中 NULL/本地 uuid → 注册 ID；设备更换（新 ID ≠ 存量）：凡仍有 pending LWW change 的实体/墓碑重打为新 ID，无 pending 的保留历史归属。
- 登出：清 toml `[auth]` + 内存 session；保留 device/workspace/binding/cursor/`device_uuid`；吊销才清 device 身份。
- **unbind（原子化）**：`lark sync unbind`（全局 `--yes`；daemon 停 + writer lock）。**(R5-P1-3) pending 防线**：存在任何未同步变更（`synced_at IS NULL`）→ **默认拒绝**并提示先 `sync run`——unbind 清 outbox/墓碑后，「以缺失表达」的未上行 song/member delete 与 `clear_lyrics` 无法由 full backfill 恢复，重绑原 workspace 时会被远端旧 create/set_lyrics 复活；确要放弃用 **`--force`（叠加 `--yes`）**，并打印将丢弃的 delete/clear 数量。序列：① drain journal（失败中止；靠 retry/discard 解锁）② 凭证原子 rename 暂存 ③ DB 事务：清 binding/cursor/sync_changes/墓碑/dead-letters/`skybridge_*` 键 + `target += 1` ④ 成功删暂存、失败还原。
- emit 自 v0.2 migration 起无条件开启。

### 3.8 dead-letter **（歧义澄清：in 存原始 envelope）**

```sql
CREATE TABLE sync_dead_letters (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  direction        TEXT NOT NULL,          -- 'in' | 'out'
  server_seq       INTEGER,                -- 检索用抽取列（in）
  client_change_id TEXT,
  device_id        TEXT,
  entity_type TEXT, entity_id TEXT, op TEXT,
  payload          TEXT,                   -- in：完整原始 ServerChange envelope JSON（含 client_local_seq / client_created_at / server_received_at，完整审计 + 可重放）；out：摘要 JSON {size, sha256, ref} 或 discard 留档
  reason           TEXT NOT NULL,
  recorded_at      INTEGER NOT NULL
);
```

- **in**：payload 校验失败与未知 entity_type/op → skip + 入表（**payload 列存整条 wire envelope**，措辞从「三件套」改为完整 envelope——server_seq 等抽取列仅为检索）。cursor 照常推进。
- **out**：emit 拒绝（超限歌词）与 file-op discard → 摘要，绝不塞大文本。
- `/sync/status` 计数 `dead_letters: {in, out}`。

### 3.9 emit 字节护栏（全 op）

所有 emit 校验整条 change 序列化 UTF-8 ≤ 240KB。歌词超限 → 本地保存 + dead-letter(out) + 事件（显式非收敛点，D3）；reorder 由 4000 上限 + 逐行 set_rank 退化兜底；其余 op 不可能超。

### 3.10 device_id 写入规则

本地 LWW 写（put 与墓碑）：`device_id = skybridge_device_id ?? NULL` 显式赋值（`songs.ts:180` 必改）；墓碑列 nullable 与业务表一致；apply 远端写 `ServerChange.device_id`；回填/重打戳见 §3.7；`sync_changes.device_id` = 本地 `device_uuid`（forensics）。

### 3.11 session 生命周期互斥

`syncEpoch` + 单一 lifecycle mutex 覆盖 {login, logout, refresh 持久化, unbind}；轮/refresh 起始捕获 epoch、副作用前复验；runSync 协作式取消。logout/teardown：bump epoch → 停触发 → abort 在途轮 → drain → 清 session/凭证 → best-effort 远端 logout → 关库。

## 9. 风险

- 传输安全：login 携带密码——默认强制 HTTPS，明文仅 localhost/双确认跳闸；现网宝塔需先上 TLS 或显式接受。
- D8 残余：重复 key 需手动清理；歧义显式报错，清理后自愈。
- 无 snapshot：大曲库新设备首拉全量回放。
- 长离线时钟漂移：注册时刻由 rebase 覆盖；运行期残余与 owl 同水位。
- 隔离目录堆积、超限歌词非收敛、file-op 永久失败——status 持久可见 + retry/discard 产品内出口。
- add 与 set_rank 之间的临时安置 rank 有短暂跨设备不一致窗口（同批相邻 seq，通常一次 pull 内收敛）——终态一致，接受。
- e2e：server（bs3 v11）与 lark（12.11.1）同进程共存 T6 验证；多进程文件 e2e 新 harness，先手工冒烟再固化。
