## §0 范围

**做**：添加页认出「这是多行」· 逐行离线判定（每行原样过 `parseSongInput`，**包括 `findSource`**——分享文本可能被整段粘进来）· 短链**逐行展开**（在选择页挂载时，不在打字时）· 选择页复用（第二个候选来源）· 关键词行**标灰且默认不勾**（用户 2026-08-24 定）· **200 行上限**（`DOWNLOAD_PARSE_LINES_MAX`，照桌面）· 目标**沿用添加页的「存到」**（照桌面：单项进当前歌单，不新建）· 整组一个命名模式。

**不做（本批）**：从文件/剪贴板批量导入 · **每行各自的目标或命名**（桌面也没有）· 歌单导入（N6）· 歌曲页多选（N4i）· 同步（N5，TLS 仍硬阻塞）· 单行输入的任何行为变化（**回归约束，见 §6**）。

**一句话的边界**：N4f 之后手机能下「一整个收藏夹」，N4h 之后它能下「你从别处攒下来的一把链接」。

## §1 开工前必须知道的

### 1.1 桌面实际怎么做的（读的是代码不是印象）

| | 桌面 | 位置 |
|---|---|---|
| 拆行 | `POST /download/parse` 逐行 `parseSongInput`，**上限 200 行** | `daemon/src/routes/download.ts` · `shared/limits.ts` |
| 展示 | 与列表组同一个对话框的「单项下载」区，默认全勾 | `BatchSelectModal.tsx:97-119` |
| 命名 | **整组一个**（`singlesNaming`），无模型时强制 `original` | 同上 `:97` |
| 目标 | **当前歌单**：`playlistId === VIRTUAL_ALL ? undefined : playlistId` | 同上 `:236` 附近 |
| 提交 | **逐条 `/download/song`，best-effort，遇到第一个拒绝就停**，toast 报 `已提交 3/5` | 同上 `submitSingles()` |

**唯一与桌面对不上的地方是最后一行**，见决策 a。

### 1.2 手机上已经有的零件

`parseSongInput`（纯函数，离线）· `resolveInput`（短链一跳）· `findSource`（**一行里挑出链接**，N4d 为分享文本写的）· `recognise`（单行薄壳）· `selection.ts`（勾选 + 去重 + 1000 上限）· `list-picker.tsx`（全屏勾选页）· `submitListBatch`（一次 `enqueueBatches`）。

**缺的只有三样**：逐行判定的函数、选择页的第二个候选来源、`submitListBatch` 的 target 参数化（现在写死 `{kind:'new'}`）。

### 1.3 🔴 一行短链 = 一次网络往返，而添加页每次防抖都重跑

单行时 `recognise` 在防抖里展开短链，那是判据 21 的「正在解析」。**多行照抄这条会变成「每敲一个字打 N 个请求」**。所以本批的时序与 N4f 一致：**打字时只做离线判定，短链的展开在选择页挂载时才发生**（决策 b）。

### 1.4 两个上限不是同一个数

**200 行**（`DOWNLOAD_PARSE_LINES_MAX`，输入的行数）与 **1000 条**（`DOWNLOAD_BATCH_ITEMS_MAX`，一次批量的条目）。本批两个都要说得出话——同 N4f §1.5 的形状。

### 1.5 一行里可能不止一个链接，也可能什么都不是

`findSource` 只在**整行读作自由文本**时启动，候选原样过 `parseSongInput`。多行时每一行独立走这条路：一行分享文本 → 认出链接；一行乱码 → 保留在列表里灰掉并带原因（决策 d）。

## §2 目标结构

### 2.1 文件布局

```
apps/mobile/src/
├── downloads/
│   ├── multi-line.ts       ← 新（N4h-1）：splitLines + 逐行判定 + 去重 + 上限，纯函数
│   └── preflight.ts        ← 改（N4h-1）：submitListBatch 的 target 参数化；

    └── add-tab.tsx         ← 改（N4h-2）：≥2 行时进多行预览与选择页
```

### 2.2 状态机（与 N4f 同一条时序）

```
粘贴多行
   ↓ （离线，零网络：逐行 parseSongInput / findSource）
[预览：N 行 · 可下载 M 条 · 不认识 K 条 · 需要模型 J 条]
   ↓ 点「下载」（还是那个按钮）
选择页挂载 ──→ [正在展开短链 3/12]（可取消 = 关掉这一页）
                     ↓
          每行一条：可下载的默认勾选；不认识的灰掉带原因；
          没模型时关键词行灰掉（用户已定）
                     ↓
          目标 = 添加页的「存到」（照桌面，不新建歌单）· 整组一个命名模式
                     ↓
          提交（决策 a）→ 回添加页，任务列表照常
```

### 2.3 提交映射

与 N4f 唯一的差别是 target：

```ts
submitBatch(deps, {
  target: playlistId === null ? { kind: 'all' } : { kind: 'playlist', playlist_id: playlistId },
  items: chosen,            // video 行 → {kind:'video', bvid, page, title:null, naming}
                            // keyword 行 → {kind:'keyword', query}
  namingMode: mode,
});
```

`title: null` 是对的：**粘来的链接没有列表标题**，命名回落到视频自己的标题（`original`）或模型（`clean`）。

## §4 判据（46–48，每条标归属）

46. **【上机】** 粘 6–8 行混合输入（视频链接 · 短链 · 一整行分享文本 · 一个关键词 · 一行乱码 · 一条重复的）→ 预览说得出「N 行，可下载 M 条」→ 点下载 → 选择页逐行列出，**乱码行灰掉带原因、重复行只出现一次**，关键词行按有没有模型决定灰不灰 → 提交 → 全部进队，**落到「存到」选的那个目标**（仅曲库或指定歌单，不新建歌单）。
47. **【单测】** 逐行判定：每行原样过 `parseSongInput`（结构检查一条不少）· 整行自由文本时走 `findSource` · 同一 bvid 只留一条 · **超 200 行当场拒绝并点名上限**（反测：去掉上限检查 → 必须红）· 关键词行的可勾状态由 `hasLlm` 决定。
48. **【单测】+【上机一眼】** 部分可用如实说：能下的能提交，不能下的**留在列表里带原因**而不是被静默丢掉；提交后不认识的那些**没有进队**。

## §5 决策（a–d，**2026-08-24 全部关闭**，下表即定案）

| # | 决策 | 倾向 | 代价 / 理由 |
|---|---|---|---|
| **a** | **提交语义**：一次 `enqueueBatches`（原子）还是照桌面逐条 best-effort | **原子一次**（用户 2026-08-24 定） | 手机上「一半成功了」很难解释，而任务列表顶部的 `M/N` 只有批次才有。**代价明写**：一条撞上容量或命名冲突会拒掉整把，而桌面会先提交前面几条再停——这是本批唯一与桌面不一致的地方 |
| **b** | **短链什么时候展开** | **选择页挂载时**，打字时只离线判定（已关闭） | 与 N4f 同一条时序。照单行那样在防抖里展开 = 每敲一个字 N 个请求 |
| **c** | **展开的并发度** | **并发 3，可取消**（已关闭） | 12 行短链串行 ≈ 12 个 RTT。并发 3 是折中；bilibili 侧没有实测过更高并发的风控口径，**这条没有测量支撑，取保守值** |
| **d** | **不认识的行怎么处理** | **保留在列表里，灰掉并显示 portable 的原话**（已关闭） | 静默丢弃会让人以为粘漏了。代价是列表更长 |

## §6 风险

| 风险 | 缓解 |
|---|---|
| 🔴 **单行行为被改坏**（判据 21 的「正在解析」、判据 25 的拒绝语、分享 intent 那条路） | 分界只有一条：**≥2 个非空行才进多行模式**，单行完全走今天的 `recognise`。现有单测（34 条）原样守着，一条都不许改 |
| **200 行的选择页卡顿** | 与 N4f 同一套：`FlatList` + 顶层一个 `Set` |
| **一把链接里混着已经在库里的歌** | 引擎按 `source_key` 去重，会 merge 成一个任务；不是本批要解决的问题，但判据 46 顺带看一眼别报错 |
| **并发展开触发风控** | 决策 c 取 3；真遇到 412/-352 就降回串行，如实记 |

## §7 本批不会证明的事

- 满载：200 行输入、1000 条批量，都只有上限常量与单测。
- 并发 3 的安全边界（没有实测支撑，见决策 c）。
- 每行各自的目标/命名（桌面也没有，不做）。
- 从文件或剪贴板历史批量导入（不做）。
