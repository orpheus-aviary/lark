## 0. 目标

1. **设置页**：Dialog 形态，编辑 llm / theme / font / log / storage / window 六段，内嵌缓存状态区块（已用/可清理/上限下拉/立即清理）；顺带「记住窗口大小」。
2. **缓存模型落地**：`cache_limit_mb` 从假旋钮变真执行——LRU 清理 + 清理前探活 fail-closed + `/cache/status`、`/cache/evict` 路由 + `cache:evicted` 事件 + 右键「固定/取消固定」。
3. **按需下载**：task kind `ensure-file` 复用引擎 `#runDownload`，播放无文件歌曲从「置灰拒播」改为「自动下载后开播」。
4. **链接体系 GUI 收口**：右键三件套（复制/打开/编辑链接）+ 编辑链接对话框 + 右键「重新下载」。
5. **导入导出**：`GET /playlists/:id/export` + `POST /playlists/import`（R27 单事务）+ 目标选择 / 疑似重复 UI（R12）。
6. **拖拽 reorder**：dnd-kit 接 M2 已就位的锚点路由。

## 2. 调查输入（2026-08-06，三路并行勘察结论摘要）

- **daemon 侧存量比预期多**：`PUT /songs/:id/pin`、`POST /songs/:id/redownload`、`POST /playlists/:id/reorder`（锚点契约）均已就位；主计划 §4 存量里缺的只有 `/cache/*` 与导入导出两组，另有本计划新增的 `POST /songs/:id/ensure-file`（M5-8，T8 回写主计划 §4 表）。`cache:evicted` 事件类型 M2 就预埋（types.ts:513，注释「only emitted from M5」），加 payload 只改一行。capabilities 是手写清单 + 双向守卫测试（system.test.ts:98），新路由不登记必红。
- **config 机制齐备**：类型在 shared `config-types.ts`；`deepMerge` 未知键保留 + `sanitize` 原地收敛；PATCH 白名单是两层字典 `SCHEMA`（config.ts:81），`[theme]` 加一行 `oneOf(THEME_MODES)` 即可（照 `LOG_LEVELS`「loader 收敛 / PATCH 拒绝」双侧样板）；`api_key` 传空串即清除（config.ts:85 注释明示）。`window` 目前只被 main 的 `windowSize()` 读（index.ts:73），无 resize 监听无回写。
- **引擎接入点干净**：`needsFile` 现有语义（engine.ts:644 `kind==='redownload' || !existsSync(...)`）恰好就是 if-missing；`ensure-file` 只需 shared kinds 数组 + `#bindTarget` 的 kind 分支 + 新增 `enqueueEnsureFile()`；`claimTypeFor`/`#execute`/`#discardUncommittedSongDir` 全部无需改。`pendingSongIds()`（engine.ts:328）M3 预留且注释写明给 M5 清理用，目前零调用方。`probeSourceKey` 已从 core 导出，清理探活直接复用。
- **两个必须补的缺口**：① `GET /audio` 拉流不取 claim，media.ts 的流注册表只有全局计数——删文件与拉流之间目前没有任何互斥/排除依据；② `last_accessed_at` 唯一更新点是 `GET /audio`（60s 去抖），新下载的歌是 null，LRU 升序会最先删它。
- **GUI 侧**：右键菜单已存在七项（含条件渲染），D8 预留的扩展位在「复制歌曲 ID」与「删除歌曲」之间；无文件歌的拦截点唯一在 `stores/player.ts:186`（UI 置灰另有四处）；`lib/prefs.ts:1-9` 注释明写设置页必须读写同一 localStorage 不得造第二真源；`stores/config.ts` 的 `adopt()` 是 M4 预留、至今无调用方——设置页是第一个消费者；**dnd-kit 未装**；`components/ui` 缺 `select`/`label`（radix-ui 伞包已装，补两个文件即可）；新增 IPC 的改动面是固定六处（shared/ipc.ts、shared/lark-api.ts、preload、main、platform adapter、test-setup 的 `defaultLarkApi`，`satisfies LarkApi` 编译期强制补全）。
- **音频/主题**：`theme/theme.ts` 是 matchMedia 自动跟随、返回的 unlisten 被丢弃；字号走 `GET /config` → CSS 变量，PATCH 后 `App.tsx:42` 的 effect 自动生效。测试范式：stub fetch 记录 calls + `useXxx.setState` 注入 + 整体替换 `window.larkAPI`。

### 4.2 缓存（T2）

- core `cache.ts` 导出（暂名）：`cacheStatus(db, opts)` 与 `runEviction(db, sqlite, opts)`；`opts` 注入 `limitBytes`、`isExcluded(songId)`（daemon 组合当前播放 + lease + 待下载，**status/预筛/重校验三个读取点共用同一实时判定**）、`streamCount(songId)`、`acquireFileClaim(songId)`（M5-5：file 类型）、`probe(sourceKey)`、`onEvicted({song_id, freed_bytes})`、`signal`。记账 = 实时扫 `songs/*/song.mp3`（曲库量级小，主计划定案不做账本）。返回 `{evicted_count, freed_bytes, skipped_unverified_count, skipped_unverified_bytes}`。
- **wire schema 冻结**（shared types.ts 新「Cache (M5)」段，GUI/CLI/后续版本按此实现，不得各自猜测）：

  ```ts
  interface CacheStatusData {
    used_bytes: number;          // songs/*/song.mp3 合计
    file_count: number;          // 有 song.mp3 的歌数
    limit_mb: number;            // 回显 storage.cache_limit_mb；0 = 不限
    eligible_bytes: number;      // 静态资格（未联网验证，M5-4）
    unreclaimable_bytes: number; // used_bytes - eligible_bytes
    limit_satisfied: boolean;    // limit_mb === 0 || used_bytes <= limit_mb * 1024 * 1024
  }
  interface CacheEvictResultData extends CacheStatusData { // status 字段为清理后重算值
    evicted_count: number;
    freed_bytes: number;
    skipped_unverified_count: number; // 按 song_id 去重：drain 多轮重复探活失败只计一次，
    skipped_unverified_bytes: number; // 后续轮次删除成功则从 skipped 集移除（M5-6）
  }
  ```

  **`*_mb` 一律按 MiB（1 MB = 1,048,576 字节）**，与 `log.max_size_mb` 同口径；GUI 上限下拉的 512MB/1GB/… 按此换算（1GB = 1024 MiB）。
- daemon 新建 `routes/cache.ts`（样板：`GET /api/instance` + `POST /download/cancel`）+ `scheduleEviction()` 调度器（setImmediate 延后 + dirty drain-loop，**AppContext 单实例**，M5-6）；`server.ts` 注册 + capabilities 登记。
- media.ts：`openAudioStreams` 全局计数 → `Map<songId, count>`，**handler 入口同步注册**（M5-5 的原子段前提；debug 路由与泄漏断言改求和，验收缝行为不变）。
- 探活即 `probeSourceKey`（pagelist 校验 bvid+cid，失败/网络错一律 null → fail-closed 跳过）。逐首探活有网络耗时：候选间无需刻意限速（曲库量级 + 探活本身有超时），但循环必须尊重 `signal`；**探活之后的复查+unlink 必须回到同一同步段**（M5-5 硬性不变量）。

### 4.4 导入导出（T6）

- shared 新类型：`PlaylistExportData` / `PlaylistImportPreviewRequest·Data` / `PlaylistImportRequest·Data` + `PLAYLIST_EXPORT_FORMAT = 'lark-playlist'` / `PLAYLIST_EXPORT_VERSION = 1`（node-free，放 types.ts playlists 段之后）。

## 6. 验收清单

**自动（自己跑，副本 nest）**：

1. 全仓 `just check` + `just test` 绿（gui 双 project 含新组件测试）。
2. 缓存演示：设 `cache_limit_mb` 小值 → 下载数首 → 手动 evict → **imported（Go 迁移 20 首）与 pinned 全部幸存**、downloaded 被删且 DB 行/lyrics.lrc 保留、`cache:evicted` 逐条到达、`/cache/status` 前后对账、`skipped_unverified` 计数正确；再验 fail-closed（伪造失效 key → 该文件跳过且计入 skipped）。流删竞态与「下载完成即可清刚下载歌」由 T2 单测锁定，副本上抽验后者一次。
3. ensure-file：删某 downloaded 的 mp3 → GUI 双击 → 下载栏出任务 → 完成自动开播（出声项留给用户）且**该文件在 lease 期内不被任何清理删掉**（含跨 drain：ensure 的 drain 结束后、/audio 未到，第二个下载触发清理 → 文件仍在——单测锁定 + 副本抽验小上限场景）；快速连点多首无文件歌 → **可取消阶段的旧任务被 cancel；已越过提交点（saving）的允许完成但不自动播放**，最终只有最后一首开播；下载中按 pause → 完成后**不**自动开播；SSE 断线期间任务完成 → 重连后仍自动开播（`reconcilePending` 对账路径）；无 key 无 LLM **且文件缺失** → 同步 400 toast（无 key 有文件照样零网络秒成）。
4. 导出→导入 round-trip：导出真实歌单 → 导入到新建歌单 → key 全命中零新建；改名一首再导 → suspects 出现且默认新条目；preview 后改文件再 commit → `IMPORT_SOURCE_CHANGED`。

## 7. 风险与注意

- **dnd-kit 架构断代**：legacy 停更（2024-12）、新架构 `@dnd-kit/react` 还在 0.x——spike 定案前不锁版不接线（M5-16 内置 gate 与备选）。
- **evict 探活打真实 bilibili**：逐候选一次 pagelist；曲库量级小可接受，但测试一律注入假 probe，真实网络只在副本验收演示。
- **清理与并发写的边界要写准**：`GET /audio` 与 `PUT /songs/:id/pin` 都不参与 claim，claim 只覆盖下载/链接编辑/删除路径——删除的安全完全靠 M5-5 的单 tick 临界区（file claim + 重读行 + 重新 stat + 排除集/计数复查，与 unlink 之间零 await），实现时任何人往这段里塞 await 都是破坏不变量；POSIX unlink 对已开 fd 无害，封的只是「已受理未开 fd」窗口。
- **main 侧 PATCH 与设置页并发**：daemon 逐请求串行、按 section 覆盖，window 段最后写者胜——语义可接受，无需锁。
- **import 20MB 同步解析 + SHA-256**：单请求 ~百 ms 级，daemon 单用户本地场景可接受；三闸防线在前。
- **两处 SSE 翻译镜像**（boot.ts / build-test-server.ts）：T2 的下载后触发（`scheduleEviction` 挂点）与 T3 的事件语义改动都要双改，M3 的既有铁律。

### 8.2 与计划的偏差（已实现为准）

1. **`runEviction(db, opts)` 不收 `sqlite`**：整段无事务，参数是多余的。
2. **`runEviction` 返回明细而非计数**：`{ evicted[], skipped_unverified[], failed[] }`。跨轮 dedup（skipped 按 song_id 去重、后续删成功即移出）必须拿到 id，计数聚合改由 daemon 的 `EvictionScheduler` 做；wire schema（`CacheEvictResultData`）未变。
3. **`streamCount` 与 `isExcluded` 保持两个注入点**（照 §4.2 原样），core 内部合成 `isReclaimableNow`，三个读取点共用。
4. **`EvictionScheduler` 的 dirty 再武装放在 `#drain` 的 finally 里**：清空在飞槽与「dirty 则再排一轮」必须在同一同步段，否则「循环判定完 → 槽清空」之间到达的触发会被记为 dirty 却没人跑。
5. **`ClaimRegistry` 不直接进 core cache**：`runEviction` 只认 `acquireFileClaim(songId) => {release} | null`，daemon 侧包一层——core 不需要知道 claim 类型体系。
6. **`ensure-file` 短路不派生歌词**：`#deriveLyrics` 只在真的取过源时跑，否则「零网络」承诺被歌词任务打破。
7. **顺带修的既有毛病**：engine 两处断言在歌词续任务仍在写 `.lyrics.*.tmp` 时读目录（T2 时序变化把它照了出来，改成按下载自身前缀过滤 / 先 `settleAll`）；Dialog 打开时全局播放快捷键让位（空格既按按钮又暂停）。

### 8.3 实测锁定（写进 CLAUDE.md 的候选，T8 汇总）

- **`config-types.ts` 的 doc 注释里不能出现 `songs/*/song.mp3`**：`*/` 提前闭合注释，Biome 报 parse error 而不是格式问题。
- **core 测试的 `source_key` 必须像真的**：`BILIBILI_KEY_RE = /^BV[0-9A-Za-z]+:\d+$/`，随手写 `bv-x:1` 会在 `createSong` 就抛 `InvalidSourceError`；同一 `(provider, key)` 全库唯一，多首歌各要各的 key（daemon 测试里给假上游的视频加多个分 P 拿不同 cid）。
- **`reconcilePending` 的语义要求快照是全量**：测试里喂单条 task 的数组等于宣告「其它 task 都没了」，会把还在等的槽清掉——喂快照就要喂全。
- **`requestPendingPlay` 后立刻对账**依赖「daemon 应答时任务已在 `/download/tasks` 里」，测试假上游要照此建模。
- **Biome 拦 `noAssignInExpressions`**：`new Promise(resolve => (release = resolve))` 这种写法过不了 lint，要写成块体。
- **jsdom 里断言 toast 文案**要 spy `toast.success`，别指望 `<Toaster />`（组件测试里没挂）。
