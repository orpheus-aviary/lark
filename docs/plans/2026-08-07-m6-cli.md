## 0. 目标

1. **跨进程写互斥**（T0）：daemon / direct CLI / migrate-go / backup-nest 四方共守 writer lock；锁序 writer → migrate → 真库；boot 的一切备份可见写在锁后（信号安装位保持 pid 锁后）；gate 写入的状态判定一律锁内（重）做。
2. **双后端**：默认 HTTP（五态身份 + 公开 nest fingerprint（显式线格式联合）+ pid 咬合）；`--direct` 读走零写入只读开库，写持锁走完整开库；direct 写仅 absent / 已证明 other-nest（本地 pid 兜底干净）放行，写永远显式 `--direct`。
3. **全命令**：§5.5 全量 + 补全；破坏性命令统一确认；错误码闭集（含 daemon 全部顶层码）+ 任务码独立集合 + 双向守卫。
4. **GUI 拉起**：统一 `ensureDaemon()`；spawn ownership、败方复验、双段硬截止的 child 回收。
5. **skill export**：模板契约测试；产物不入备份；可用性验收挂 M7。
6. **agent 友好**：全局 `--json`（exit 0 ⇔ stdout 恰好一个成功信封）、stdout/stderr 分流、非 TTY 一律显式 `--yes`。

## 2. 调查输入（2026-08-07，三路并行勘察 + 五轮评审逐项对代码复核）

- **CLI 骨架**：5 文件一命令；`backend/types.ts` 冻结 R31 与信封纪律；鉴权空缺。
- **daemon 锁形态**：pid 文件 O_EXCL——启动互斥非写互斥；现有 `readPid` 非纯读（ESRCH 即 unlink stale）。M1 先例：常驻 SQLite 锁库（fcntl，kill -9 自动释放，永不删除）。
- **boot 顺序**：现行 mkdir → loadConfig（缺失写默认、宽权限 chmod）→ createLogger → acquireDaemonLock → **立即安装信号处理器**（生命周期不变量：pid 文件存在期间信号必走状态机；boot.child 测试断言之）→ createDatabase → …——config 写在锁前（四轮 P0）；信号位不可后移（五轮①）。
- **鉴权面**：`/status` 唯一公开；`/api/instance` 鉴权后才给 `nest_dir`——跨 nest token 天然不同（四轮 P0 → 指纹协议）。
- **stop 协议**：daemon `./cli` 五步 ≤5s。`probeRunningDaemon()` = /status + pid 双探测。
- **createDatabase**：恢复/WAL/迁移/device_uuid；五路分派 + `assertSchemaV1`。M4 锁定：只读打开 WAL 库仍造边车。**`existsSync` 对 EACCES 也返回 false**（五轮②——缺失探测须 `statSync` 仅认 ENOENT）。
- **migrate-go**：peek 在锁前、排他升级无条件写 `user_version=0`（三轮 P0）；swap 对旧 inode 写者无防护。
- **config**：`loadConfig()` 缺失写默认；不安全口径 = `(mode & 0o077) !== 0`（0700 放行）。
- **backup-nest**：先复制后排他（二轮 P0）；skip 清单 = RUNTIME_ENTRIES + DB_ENTRIES。
- **download 限额**：parse 先验 8192 字符再验 200 行；batch keyword 另限 500；`TERMINAL_RING=100`、`BATCH_RING=20`；队列 1000、batch ≤20 组/1000 条、fetch-list ≤200 页/5000 条；batch 返回 `{batches:[...]}`。
- **错误码表面（五轮③复核）**：同步路由另有 `BILIBILI_FAILED` / `BILIBILI_RISK_CONTROL` / `NORMALIZE_FAILED` / `PREFLIGHT_TIMEOUT`；全局处理器保留 `BAD_REQUEST` / `INTERNAL_ERROR`；**任务对象内嵌套 `TaskErrorCode`**（`LLM_FAILED` / `SOURCE_GONE` / `FFMPEG_FAILED` / `DOWNLOAD_COMMIT_FAILED` 等）不在信封 `error_code` 上。
- **direct 地基**：core 全套 CRUD/transfer/cache/config，双句柄；core 错误多数非 CodedError；路由层输入契约/enrichment/虚拟 all/20MB 无 core 对应物。
- **daemon 表面**：52 条路由；无 HTTP shutdown；player 四态（ack 3s）；`LOCAL_API_VERSION=2` 在 `@lark/daemon/version`。
- **owl CLI**：backend 四件套 + `decideMode` 纯函数、闭集错误码、退出码 7 档、stdout/stderr 分流、token seam、skill 模板契约。
- **GUI spawn 卫生（M4-2）**：child 确权才 owned、超时回收、败北后复验胜者、绝不注入 token、绝不停陌生进程。

### 8.2 计划外的实施决定（都在 T0 内定，可推翻）

1. **`fail()` 与 `InvalidRequestError.code` 一并收紧到注册表**（计划只要求 `STATUS_BY_CODE` 对表）。只做 `STATUS_BY_CODE` 挡不住「路由 `fail()` 里写了个没注册的码」——收紧参数类型后每个发射点都编译期受检，代价是 errorHandler 里 Fastify 的 `FST_ERR_*` 需显式收窄（原来直接原样发给客户端，而客户端对它本就没有映射）。
2. **migrate-go 只读探测的 busy_timeout 收到 2s 并映射成 `MigrationBusyError('exclusive_lock_busy')`**。原来走 better-sqlite3 的 5s 默认，遇到「另一个迁移器持有源库 EXCLUSIVE」会先卡满 5 秒再抛裸 `SQLITE_BUSY`；这个条件本来就有名字。
3. **backupNest 的 skip 要覆盖锁库的 `-journal` 边车**（计划只写了两个锁库文件名）。备份现在自己持写锁，所以 `songs.db.writer.lock-journal` 在 `readdir` 那一刻**必然存在**——按前缀跳过而非精确名。
4. **迁移锁的获取移进 `try`**：写锁与迁移锁之间抛错（`migrate_lock_busy` 就是）会把写锁泄漏到进程结束。测试是先红后绿的。
5. **daemon `daemon-status` 改用 `inspectPidReadonly`**：原来走 `readPid`，会把 stale pid 文件当场删掉——一个只回答问题的命令不该有副作用。
6. **boot 的生命周期日志加 console 兜底**（`lifecycleLog`）：logger 现在在写锁之后才建，而信号处理器在写锁之前就装好了，这段窗口里的 stop 只能走 stderr。
7. **`MigrationPendingError` 暂无真实夹具**：`LATEST_KNOWN_VERSION` 还是 1，`0 < v < LATEST` 不可达，只能直接断言错误类本身——等 v2 落地再补分派用例。

### 8.3 T0 实测锁定

- **`BEGIN EXCLUSIVE` 会在锁库旁边留 `-journal`**：持锁期间它一定在，凡是「遍历 nest 目录」的逻辑都要按前缀排除两个锁库
- **同进程两个连接照样互斥**：SQLite 的 unixFile 在进程内自己记 inode 锁状态，所以 `Promise.allSettled([migrate, migrate])` 这种同进程并发能真实复现败方被拒
- **写锁只挡写者，不挡读者**：读路径不取写锁，但会撞上 migrate-go 给源库上的 `locking_mode=EXCLUSIVE`——那是 SQLite 层的锁，只能靠 busy_timeout 等或超时报错
- **`expect(fn).toThrow(predicate)` 在 vitest 里不是「谓词断言」**：要区分错误类型得自己 try/catch 后 `expect(caught).not.toBeInstanceOf(...)`

2. **`sanitizeFileName` 下沉 shared**，GUI 的 `dialog-ipc` 改为复用。写 CLI 那份时手抄的字符类把控制字符范围抄丢了，变成会**吃掉空格和连字符**（"Late Night" → "LateNight"）且不过滤控制字符——是 biome 的 `noControlCharactersInRegex` 报出来的。两份同样的规则本来就该只有一份。

**实测**（临时 nest × 真实 daemon）：导入 2 首 → 列表 → 按名字 pin → 歌单成员 → reorder（顺序真的换了）→ `--json` 编辑 → 非 TTY 无 `--yes` 删除被拒(2) → `--yes` 删除 → 列表少一首；`playlist export "Late Night / 深夜" -o <目录>` 落成 `Late Night  深夜.lark-playlist.json`（斜杠没造出子目录，空格保住）。

**实测锁定**：
- **`search` 只是预筛，不是判定**：daemon 的 `search` 是 `LIKE %s%`，所以「晴天」会捞出「晴天娃娃」；`resolveSongRef` 必须在结果里做精确名匹配，>1 才是 `AMBIGUOUS_SONG`。
- **SQLite 的 `LIKE` 对 ASCII 大小写不敏感**：fake backend 一开始写成 `includes()`（大小写敏感），于是「大小写回退」的用例假红——假后端比真 daemon 严会制造不存在的 bug。
- **批量删除要先全解析再动手**：「删两首、第三个名字有歧义」比「一开始就拒」难收拾得多。

### 8.6 T3 direct 后端 + cache 组（2026-08-07）

落地：`backend/{direct,direct-errors}.ts` + `commands/cache.ts` + `withContext` 的 direct 分支（唯一一处 `await import('@lark/core')`）+ 集成测试 `backend/direct.test.ts`（真实库、真实写锁）。CLI 测试 169 → 184。

读走 `openDatabaseReadonly`（不取任何锁），写先取 writer lock 再 `createDatabase`；`withContext` 的 `finally` 负责 close——写锁是跨进程资源，漏掉会让下一次 daemon boot 白等满 5 秒。

**两处偏差 / 发现**：

1. **错误映射按类名匹配，不用 `instanceof`**。core 是**动态 import** 进来的，模块对象和静态 import 的不是同一个，`instanceof` 会看运气。每个 core 错误类都在构造函数里设 `this.name`，按名字匹配同样可靠且不钉死模块图。
2. **两个真实的双后端差异是冒烟测出来的**（不是想出来的）：
   - `getSong('nope')` 直连返回 `NOT_FOUND`，HTTP 返回 `INVALID_ID`——路由层有 uuid 门禁而 core 只会「查不到」。direct 侧补了同款 `validId` / `readableId` / `writablePlaylistId`。
   - `playlist list --direct` 少了虚拟 `all`——它不是行，core 不会返回，是 daemon 路由拼上去的。不补的话「按名字引用歌单」会随「daemon 在不在」给出不同结果。补齐后两边输出逐字相同。

**归 T7 的**：真 daemon × direct 的**领域错误逐条对拍**放进 `just accept-cli`（§6 判据 10）——单元测试里没有真 daemon，只能各测各的映射。

### 8.7 T4 download + url + lyrics（2026-08-07）

落地：`lib/{download-input,wait}` + `commands/{download,url,lyrics}` + Backend 增九个方法（HTTP 全实现；direct 只认 `deleteLyrics`，其余八个 daemon-only 显式拒绝）+ `withBackend` 的 precheck 缝。CLI 测试 184 → 266。

命令树：`download [input]`（`--batch <file|->` / `--playlist` / `--wait` / `--no-wait` / `--allow-partial`）、`songs redownload`、`songs url get|set|recognize [--save]`、`lyrics redownload|delete`。三种形状由 `/download/parse` 判定：单条 → `/download/song` 默认跟到终态；收藏夹 / 合集 → `fetch-list` → 明细 → 确认 → batch；多行 → 一个 group 的 batch，`--wait` 可选。

**四处偏差 / 计划外**：

1. **keyword 500 的预检放在 parse 之后**（计划写的是「本地逐行预检」）。本地判不出哪一行是关键词——只有 `/download/parse` 知道，而按「不像链接就是关键词」的启发式判，600 字符的长 URL 会被误杀。放在 parse 之后仍然按**行号**报错（items 与行一一对应），代价只是那一次本来就要发的 parse 请求。8192 的单行上限仍在本地、在 parse 之前——超长的行根本装不进任何一个分块。
2. **位置参数允许多行**：`lark download "$(pbpaste)"` 粘进来的多行按 batch 走，与 GUI 粘贴框同规则。`--batch` 只决定**来源**（文件 / stdin），不决定形状。
3. **`withBackend` 加 precheck 缝**：参数形状的判定必须跑在**探测 daemon 之前**。原来 `lark download`（零参数）在没有 daemon 时报的是 `DAEMON_UNAVAILABLE`(4)——把用户支去启动一个同样会拒绝它的 daemon。现在 `assertDownloadShape` 在 `withContext` 之前跑，零参数与 `<input> + --batch` 同给都是 `USAGE_ERROR`(2)。T5 的「`play` 零参数 → 2」直接用这条缝。
4. **`lyrics delete` 直连不取 claim**：daemon 用 `lyrics` claim 关掉「探在不在」与「删」之间的窗口；直连模式下这个窗口不存在——R31 保证没有 daemon，写锁排掉其余三方写者。

**一个真实缺陷（冒烟抓到）**：`songs url recognize <song>`（不给 url）原本发**无 body 的 POST**，daemon 的 `objectBody` 直接判 `INVALID_BODY`(2)。改成发 `{}`。`redownload` 与 `download/lyrics/:id` 不读 body，无 body 的 POST 照常能过——同样是 POST，能不能省掉 body 取决于路由读不读它。

**实测**（临时 nest × 真实 daemon × 真实 bilibili）：单条 URL `--wait` 走完 解析地址 → 下载音频 → 转码 → `✓ 完成`（3.7s）；两行 `--batch` 文件（含 `#` 注释与空行）+ `--playlist 深夜` + `--wait` → `… 已完成 0/2 → 1/2 → ✓ 2 条全部完成`，歌单里真有两首；多分 P 视频无 `?p=` → `LLM_NOT_CONFIGURED`(3) 并报出真实分 P 数；`songs url set` 撞别人的 key → `SOURCE_KEY_CONFLICT`(5) 带 `conflicting_song_id`；`lyrics delete` 非 TTY 无 `--yes` → (2)，`--yes` → 删掉，再删 → `LYRICS_NOT_FOUND`(1)；重复下载同一个链接 → 绑回同一首歌 exit 0。

**归 T7 的**：真实收藏夹 / 合集的 `fetch-list` 链路（判据 13）——手边没有可复现的公开 media_id，单测走的是 stub 列表。

### 8.8 T5 play / gui / daemon 生命周期（2026-08-07）

落地：`lib/{launch,ensure-daemon}` + `commands/{player,gui,daemon}` + Backend 增 `playerStatus` / `playerCommand` + `context.ts` 的 `launch` 分支接上 `ensureDaemon` + `index.ts` 的 `withIdentity`（管理命令不取后端）+ `testing/{fake-child,fake-identity}`。CLI 测试 266 → 323。

命令树：`daemon` / `stop-daemon` / `play [song] [--playlist] [--no-launch]` / `pause|resume|next|prev` / `seek <秒>` / `mode <模式>` / `now-playing` / `gui`。

**五处决定 / 偏差**：

1. **只有 `play` 有拉起链**（§4 矩阵本就只在 `play` 行写了「拉起链」）。`pause` 为了暂停一片寂静而开一个窗口不是便利；GUI 不在线时它们拿到 daemon 的 `GUI_OFFLINE`(4)，文案已经在说「先开 GUI」。`now-playing` 同理，只读不拉起。
2. **`IdentityHandle` 抽出 `IdentityResolver` 接口**。class 有私有字段 = 名义类型，测试要脚本化「absent → current」就得去伪造 socket 和 pid 文件。接口只有 `resolve` / `resolveFresh` 两个方法，正好是 `ensureDaemon` 需要的全部。
3. **管理命令的 `--direct` 拒绝落在 `withIdentity` 里**，`status` 一并纳入——M6-22 写了「管理命令收 `--direct` → `USAGE_ERROR`」，但 T1 的 `status` 当时是裸 `run()`，没有这条。
4. **stop 的两种非成功终局分别给码**：协议拒发信号（pid 失配 / 不可证）→ `DAEMON_UNVERIFIED`(5)，发了 SIGTERM 但 5s 内没退出 → `SHUTTING_DOWN`(4)（「它正在走，等会儿再看」正是这个码的语义）。不新增码。
5. **GUI 定位读 `node_modules/electron/path.txt`**，不 import electron——守卫 `cli-no-daemon-gui` 会拦 `require('electron')`，而 CLI 需要的只是一个路径字符串。daemon 侧同理：`process.execPath` + `packages/daemon/dist/cli.js`。两个定位函数都在 `lib/launch.ts` 一个文件里，标了 M7 SEAM。

**一个真实缺陷（冒烟抓到，会开窗口的那种）**：`lark play --playlist all --no-launch` **真的启动了一个 GUI 窗口**。commander 把 `--no-launch` 存成 `launch: false`，从来不是 `noLaunch: true`——按声明时的名字去读，这个 flag 就是静默失效的。改成显式翻译函数 `playOptionsFrom(raw)` 并配回归测试；`canLaunch` 也走同一个翻译。

**实测**（临时 nest × 真实 daemon）：`lark daemon` 冷启动 0.6s 返回 `{started:true,pid}` 且**父进程立刻退出**（`stdio:'ignore'` 的意义）→ 再跑一次 `{started:false}` 同 pid → `status` 在线 → `now-playing` 报「GUI 没有在线」→ `pause` 拿到 `GUI_OFFLINE`(4) → `play --no-launch` 零 spawn exit 4 → `seek abc` / `mode random` 本地拒 exit 2 → `--direct daemon` exit 2 → `stop-daemon` 停掉并确认 → 再跑一次幂等 exit 0 → `status` exit 4。

**归 T7 / 用户手动的**：GUI 冷启动链（判据 22，要看窗口和听声音）；`lark gui` 的真实 Electron 启动只在这次事故里被动验证过一次（窗口确实起来了并注册成功），正式验收还是 headless 之外的事。

**实测**（临时 nest）：空库 direct 读 → `DB_NOT_INITIALIZED`(3)；无 daemon 写不加 `--direct` → exit 4；`--direct` 导入 → 直连读 → pin → cache status（且**没有**生成 config 文件）；daemon 起来后 `--direct` 写 → `DAEMON_RUNNING_BLOCKED`(5)、`--direct` 读照常；停机后 `--direct` 写恢复。
