## 0. 为什么还需要人跑一遍

`accept-sync` 的 server 在 127.0.0.1，两个设备在同一台机器上，整轮不到十分钟。它证明不了三件事：

1. **明文 HTTP 的跳闸在真实地址上确实会拦**——loopback 是被豁免的那一档，本地永远走不到那条分支；
2. **凭证会过期、会刷新**——access token 默认 30 天，refresh 180 天，只有真实时间（或服务器上临时调短 TTL）能验；
3. **网络会断**——公网抖动、笔记本合盖、服务器重启，这些是同步真正会遇到的日常。

## 1. 前置

### 1.1 服务器（阿里云 Ubuntu + 宝塔 + PM2，见 `owl/docs/deploy/baota-fish-runbook.md`）

`@orpheus-aviary/skybridge-{proto,client,server}` 的 npm `latest` 已经是 **0.1.4**（2026-05-31 发布），lark daemon 精确钉 client/proto **0.1.4**，所以服务器只需升到同版本，不需要为 lark 发新包。

```fish
cd /www/skybridge
npm install @orpheus-aviary/skybridge-server@latest
npm rebuild better-sqlite3                       # Node 24 无预编译（踩坑 3）
node_modules/.bin/skybridge-server --init --config /www/skybridge/server.toml
pm2 restart skybridge
pm2 describe skybridge | grep -E "exec mode|instances"   # 必须 fork / 1（单实例不变量）
curl -s http://127.0.0.1:8443/v1/health
curl -s http://127.0.0.1:8443/v1/server-info             # 记下 server_id
```

- [ ] **P1** 服务器版本 = 0.1.4，`/v1/health` 与 `/v1/server-info` 都答；`exec mode: fork` / `instances: 1`
- [ ] **P2** **8443 对公网放行且锁源 IP**：阿里云安全组 + 宝塔系统防火墙**两处**，授权对象 `<你的公网IP>/32`
      （owl 不需要这条——owl-server 走 loopback 连 skybridge；lark 桌面端是直连）
- [ ] **P3** 本机 `curl -s http://<公网IP>:8443/v1/health` 通
- [ ] **P4** 建一个**专供 lark soak 的账号**（不要复用 owl 的 owner）：
      `node_modules/.bin/skybridge-server --config … user create --email lark-soak@… --password '<强密码>'`

### 1.2 本机两个设备

lark 0.2 还没打包，两台都跑仓库产物：

- **设备 A**（有 GUI）：`just backup-nest ~/lark-soak-a` 出一份真实曲库副本 → `LARK_NEST_DIR=~/lark-soak-a`
- **设备 B**（只有 daemon）：全新空目录 `~/lark-soak-b`，用 `packages/daemon/dist/testing/boot-child.js` + `LARK_DAEMON_TEST_PORT=47101` 起，HTTP 驱动

- [ ] **P5** A 的曲库副本已升到 schema v2（GUI 起一次即可），B 是全新空库
- [ ] **P6** ⚠️ **不要用真实 nest**：真实曲库一旦被 v0.2 daemon 打开就升到 v2，已发布的 0.1.0 会拒绝再打开它

## 2. 明文 HTTP 的跳闸（自动判据到不了的那一档）

服务器是 `http://<公网IP>:8443`，非 loopback，所以两条入口都必须逼你表态两次。

- [ ] **S1** GUI：设置 → 同步 → 填 `http://<公网IP>:8443` **不勾**「允许明文 HTTP」→ 点登录
      **期望**：不发请求，提示「服务器地址不是 HTTPS……请勾选下面的选项」
- [ ] **S2** GUI：勾上复选框 → 再点登录 → **期望**：弹二次确认（说明代价），取消则**零请求**
- [ ] **S3** GUI：确认后真登录成功；`~/lark-soak-a/lark/skybridge.toml` 里 `allow_insecure_http = true`，权限 `0600`
- [ ] **S4** CLI（设备 B 那侧同理，用 HTTP 直调 `/sync/login` 时带 `allow_insecure_http: true`）：
      `lark sync login --server http://<公网IP>:8443 --email … --password-stdin` **不带** flag → 退出码 2 / `SYNC_INSECURE_URL`
- [ ] **S5** 加 `--allow-insecure-http` 但**不带** `--yes`、且非 TTY → 退出码 2 / `USAGE_ERROR`，什么都没发出去

> 上了 TLS（Caddy 反代 + 域名，见 `skybridge/docs/deploy/ubuntu-baota.md` §11）之后，S1–S5 应当**全部不再出现**——那也是一条判据。

## 3. 两台设备的日常

每步之后：A 看 GUI 徽章，B `curl -s -H "Authorization: Bearer $TOKEN_B" http://127.0.0.1:47101/sync/status | jq .data`。

- [ ] **D1 首次回填**：A 登录 → 徽章从「未启用同步」变「已同步」；曲库全部上行（`pending` 归零，`pushed_seq` > 0）
- [ ] **D2 新设备首拉**：B 登录 → B 的空库拉到 A 的全部歌 / 歌单 / 歌词；两边 `songs` 数一致
- [ ] **D3 歌词跨设备**：A 给一首歌下载/编辑歌词 → B 的 `songs/<id>/lyrics.lrc` **真的出现在磁盘上**（文件效应，不是元数据）
- [ ] **D4 歌曲本体不同步**：B 上那首歌是「需要下载」状态，`songs/<id>/song.mp3` 不存在——本体按 `source_key` 各自下载
- [ ] **D5 双向编辑**：A 改歌名、B 改歌手 → 两轮之后两边都拿到对方的改动，且互不覆盖
- [ ] **D6 歌单顺序**：A 拖拽排序 → B 在**两轮之内**收敛到同一顺序（第一轮可能抖一次，⚡ op 要等自己的回声）
- [ ] **D7 冲突**：断开 B 的网络（或先不同步），两边改**同一首歌的同一字段** → 恢复后落败方出现冲突徽章 →
      冲突页两栏值正确 → 「保留本机」后两边收敛到保留的那份
- [ ] **D8 远端删除 + 隔离**：B 删掉一首 A 本地有文件且**无法重下**（imported）的歌 →
      A 的文件进 `~/lark-soak-a/lark/recovered-songs/<song_id>/`，`sync status` 报「已隔离 1 首」；**重启 A 后计数仍在**
- [ ] **D9 重复来源**：两边各自把同一个 bilibili 链接贴到不同的歌上 → 两首都活着，列表里各带 `[重复]`，
      `lark songs list --duplicates` 列出这两首；删掉多余的一首后提示消失

## 4. 真实网络与真实时间

- [ ] **N1 服务器重启**：`pm2 restart skybridge` → A/B 的下一轮自愈（可能先看到「同步离线」，不需要重新登录）
- [ ] **N2 断网**：关掉 Wi-Fi 5 分钟，期间在 A 上继续编辑 → 徽章「同步离线」而不是「出错」；恢复后未推送的改动全部上行，无丢失
- [ ] **N3 合盖 / 睡眠**：合盖 30 分钟以上再打开 → 下一轮正常，不出现 401 也不要求重新登录
- [ ] **N4 refresh 轮换**（要么等，要么在**非生产实例**上把 `[auth].access_ttl_sec` 调到 120 再重启）：
      access 临近过期时自动换新 → 服务器 `refresh_tokens` 里旧行 `replaced_by` 非空；期间 A 不需要人工干预
      ⚠️ 生产实例不要改 TTL（owl 的 S5b 结论：忘了改回去会让该实例上之后所有会话高频 refresh）
- [ ] **N5 长跑**：GUI 开着挂 24 小时 → 服务器日志无高频 `/v1/auth/refresh`、无 5xx；A 的 `lark.log` 无重复告警刷屏
