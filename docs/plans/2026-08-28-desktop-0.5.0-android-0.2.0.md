> **性质**：一个里程碑的子计划，按仓库规矩**先过目再动手**。每批一次提交，复杂的拆多个；提交前把 commit 信息给用户看。
> **口径**：2026-08-28 用户按实际使用列出的 7 条 + 追加的第 8 条（清洗命名的多歌手规则）。

## 0 · 这一版是什么

八条。**两条是 bug**（① 输入法回车、⑥ 歌词滚不到尾），其余是产品形状与新功能。

代价最大的三块，按大小排：**桌面歌词**（一个全新的 Electron 窗口 + 一节配置，⑤）· **下载来源与记录持久化**（唯一一处双端同时动、且线协议变宽，④）· **手机歌词的中线跳转**（⑦）。其余五条是界面账与一行提示词。

## 2 · 三条要先说清的调查结论

### 2.1 输入法：全仓零防护，不是某一处漏了

`isComposing` / `compositionstart` 在**整个仓库零命中**。Chromium 在候选词上按回车时 `e.key` 仍然是 `'Enter'`，唯一能区分的是 `e.nativeEvent.isComposing`（老式输入法还会给 `keyCode === 229`）。所以这不是「下载栏写漏了」，是**这个 app 从来没有过输入法这一层**。

五处 Enter 处理全部中招：

| 位置 | 后果 |
|---|---|
| `DownloadBar.tsx:166` | **用户报的那个** —— 组字中回车 → 拿拼音当关键词去 B 站搜 |
| `TopBar.tsx:150` | 歌单新建 / 重命名，拿拼音当歌单名 |
| `SongRow.tsx:164` | 歌名行内改名，同上 |
| `BatchSelectModal.tsx:395` | 批量弹窗里的分组名 |
| `settings/SyncTab.tsx:149` | 登录，组字中回车直接发请求 |

`SongRow.tsx:498` 那处**不在名单里**：它是表格行的键盘激活，不是输入框，组字不会落到它上面。

**曲库搜索框（`TopBar.tsx:290`）是另一种形状**：它根本没有 Enter 处理，是 `onChange` + 400ms debounce —— 而 `onChange` 在组字过程中照样触发，所以打「青花瓷」会先拿 `qing`、`qinghua` 各搜一次。修法不同（组字期间不提交 debounce），但属于同一条账。

`useKeyboardShortcuts.ts` **不用改**：它的 `isTyping()` 已经在按键分发前挡掉了所有 `INPUT` / `TEXTAREA` / `contentEditable`。

### 2.2 下载来源：批量入队把身份和 `?p=` 都丢了

现在任务上只有 `DownloadTaskInput` 三种形状，能回答「从哪来」的只有前两种：

| 来源 | 现在拿不拿得到 |
|---|---|
| 关键词搜索 | ✅ `input.query`（今天只当 tooltip 用：`DownloadPanel.tsx:117` 的 `title=`） |
| 单个视频链接 | ✅ `input.url`，**带 `?p=`** |
| 收藏夹 / 合集 / 多行粘贴 | ❌ **身份完全没有，`?p=` 也丢了** |
| 重新下载 / 按需下载 / 歌词 | ❌ 只有 `song_id`（歌行上另有 `source_url`） |

第三行是关键，且不是「界面没画」而是**数据不存在**：`engine.ts:390` 给批量的每一条建的 input 是写死的

```ts
{ type: 'url', url: `https://www.bilibili.com/video/${target.bvid}` }
```

—— 合集/收藏夹的名字从来没进过请求体（`DownloadBatchGroupInput` 只有 `target` 和 `items`），而 `page` 明明就在 `DownloadBatchItemInput` 上，**却没被写进 url**。后者顺带是一个既有 bug：手机的「重下」走 `record.input.url` 重放，一个多 P 视频重下会回到 p1。

所以 ④ 必须给任务加字段，绕不过去。

### 2.3 桌面歌词：没有可依赖的现成组件

搜了一圈，**npm 上没有能装的组件**。搜到的全是整只应用，只能当参考实现：
[MeT-Music](https://github.com/MeTerminator/MeT-Music_App)（Electron，带桌面歌词，支持置顶/锁定/配色）·
[qq-desktop-lyrics](https://github.com/amadoncy/qq-desktop-lyrics) ·
[spotify-lyrics-overlay](https://github.com/EvansLR/spotify-lyrics-overlay)。
[`electron-overlay-window`](https://www.npmjs.com/package/electron-overlay-window) 名字像但不是这件事 —— 它是「把窗口贴到**别的进程**的窗口上」。

结论：**自己写**，量级约 300–400 行。技术上都通，四个要点：

1. **盖在全屏应用上**：`setAlwaysOnTop(true, 'screen-saver')` + `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })`。只 `alwaysOnTop: true` 压不住全屏。
2. **锁定 = 整窗穿透**：`setIgnoreMouseEvents(true, { forward: true })`。macOS 上有个已知坑（[electron#23042](https://github.com/electron/electron/issues/23042)）—— 穿透是整窗生效，**没法只让某个元素可点**，社区补丁 [`@loomhq/electron-click-through-workaround`](https://www.npmjs.com/package/@loomhq/electron-click-through-workaround) 就是治这个的。**我们不踩这个坑**：用户定的语义本来就是整窗穿透。
   🔴 **但它有个直接后果**：锁定之后歌词窗上任何按钮都点不到，**解锁的唯一出口是 GUI 设置页** —— 这正是用户要的形状，但设置页的文案必须写明，否则读起来像卡死。
3. **歌词数据走 IPC，不走 daemon**：播放本来就在主窗的 `<audio>` 上，`usePlayer` 已经有 `currentTime`（timeupdate）和解析好的 `lyrics`。让歌词窗自己连 daemon 要多一套 token 与 CSP，而且 `/player/report` 是 2 秒一次的粗粒度，**行级同步会抖**。
4. **配置归属**：M4-12 / M5-2 冻结过一条线 —— **外观进 config，视图状态进 localStorage**。桌面歌词的开关/字号/配色是外观，窗口位置尺寸照 `[window]` 的先例（`window-memory.ts` 已经有一份 debounce 回写）。所以整节进 `lark_config.toml`，也就必然抬协议号。

## 3 · 协议、版本与门禁

### 3.1 为什么抬到 9

两条，都和当年抬到 6、抬到 8 **逐字同形**（`api-paths.ts` 的注释块就是判据）：

- **`[desktop_lyrics]` 配置段**：8 的 daemon 对 `PATCH /config` 里的未知 section 答 `INVALID_CONFIG: unknown config section`。设置页要写它 ⇒ 一个写着 9 的 GUI 没法通过 8 的 daemon 用自己的功能。
- **`POST /download/batch` 的 `source`**：`validation.ts:50` 的 `objectBody` 对未知 key 一律 400 `INVALID_BODY: unknown field: source`。**这一条比配置那条更硬** —— 不是功能降级，是整个批量下载被拒。另有三个新端点 `GET/DELETE /download/history`，8 的 daemon 一律 404。

### 3.2 版本号一起动的十三处

0.4.1 那次是十一处；这一版多了 Android 的两个：

六个 manifest（root · shared · core · daemon · gui · cli）· 三个常量（`daemon/src/version.ts` · `gui/src/shared/version.ts` · `cli/src/version.ts`）· 协议号（`shared/src/api-paths.ts`）· `scripts/accept-pack.mjs` 的 `EXPECTED_API_VERSION` · `apps/mobile/app.config.ts` 的 `version` **与 `versionCode`**。

⚠️ **设备注册的 `app_version` 不用单独动**：`coordinator/login.ts:344` 写的是 `lark ${ctx.version}`，`ctx.version` 由宿主注入，跟着上面的常量走。（owl 0.6.0 在这里漏过一次，lark 的形状不同，记一笔备查。）

### 3.3 门禁

- `just check` 的守卫从**十二条变十三条**（新增 IME 守卫，见 P1）。
- 五套 accept：`accept-gui` 15 · `accept-cli` 27 · `accept-m5` 22 · `accept-sync` 36 · `accept-pack` 28 = **128**。这一版会给 `accept-pack` 加一条（打包产物里必须有歌词窗那份 html，见 P9b），届时是 **129**。
- ⚠️ `accept-sync` 默认拿 `local` 库去复制，而本机 `active` 是账号库 —— 0.4.2 那次踩过（`SQLITE_CANTOPEN`）。跑之前先确认工作区形状。

## 4 · 分批

> 每批 = 一次提交（拆开的按 a/b/c 各一次）。判据一律要能说出**它怎么变红**；说不出就别加。
> 手机端新增的判定**必须落在 Node 能加载的模块里**并加进 `apps/mobile/vitest.config.ts` 的 include —— 那是显式列表，不加等于没测。

**顺序的理由**：先桌面小改（不动协议、不动手机，笔记本上就能验红，最便宜的价值先落地）→ 再手机 UI（效果全部要设备答，早进树，好让后面所有批次叠在同一份手机代码上）→ 再双端的下载来源与记录（唯一一处两端同时动，也是线协议变宽的地方）→ 再桌面歌词（最大，但纯桌面、不阻塞任何人）→ 抬版本号 → **一次**真机会话 → 发版。

### P1 · 输入法组字期间不许提交（①）

`fix(gui): let the IME keep the Enter that commits a candidate`

**改什么**
- 新增 `renderer/src/lib/ime.ts`：`isComposingKey(e)` = `e.nativeEvent.isComposing || e.keyCode === 229`。两个条件都要 —— 前者是标准，后者是老式输入法在部分平台上的唯一信号。
- §2.1 表里的五处 Enter 处理各加一道门。
- 曲库搜索框另一种修法：`onCompositionStart` 置位、`onCompositionEnd` 复位并立刻提交一次，组字期间 debounce 不提交。**不要**用「猜是不是拼音」这类启发式。

**判据**
- `ime.test.ts`：两种信号各一条，都不是组字时放行。
- `DownloadBar.test.tsx`：`fireEvent.keyDown(input, { key: 'Enter', isComposing: true })` **不**调 `parse`；`isComposing: false` 调。⚠️ 先确认 jsdom 的 `KeyboardEvent` 认 `isComposing` 这个 init 字段；不认就退到 `keyCode: 229` 那条，并在测试里注明为什么。
- `TopBar.test.tsx`：组字期间打字不触发 `setSearch`，`compositionend` 之后触发一次。
- 新守卫 `scripts/check-gui-ime-guard.sh` + `just` 一条 recipe：renderer 里凡是出现 `key === 'Enter'` 的**文件**必须同时出现 `isComposingKey`。**破法**：删任意一处门 → 红。

### P2 · 一次被放弃的解析回到它来的地方（② + 补充决策第四条）

`feat(gui): send an abandoned parse back to where it came from`

**改什么**
- `PasteInputModal` 加 `initialText` prop（内部 `useState(initialText)`）。
- `DownloadBar` 持有 `parsedFrom: { origin: 'inline' | 'paste'; text: string } | null`。**`submit()` 的三种去向全部登记它**，不只是批量那一种：
  | 解析结果 | 去向 | 放弃时 |
  |---|---|---|
  | 单个关键词 | 立刻下载 | 没有放弃这一步，`parsedFrom` 用完即弃 |
  | 单个视频 | `NamingModeDialog` | **取消 → 回原处**（补充决策第四条） |
  | 其余 | `BatchSelectModal` | **返回 → 回原处**（②） |
- 回原处按 `parsedFrom.origin` 分岔：
  - `inline` → `setValue(text)` + 聚焦单行框，粘贴框**不开**
  - `paste` → `setPasteOpen(true)` + 回填原文
- `BatchSelectModal` 底部**从「取消 + 确认」变成「返回 + 确认」**，只留一颗返回（用户定：防误触，真想取消再返回一层不麻烦）。
- 弹窗里的勾选 / 组名 / 原标题**一律不保留**：返回就是要重新解析，而重新解析出的 items 可能和上次完全不同，硬对齐比丢掉更怪。

**判据**
- `BatchSelectModal.test.tsx`：底部只有一颗非确认按钮，点它调 `onBack` 而不是 `onClose`。**破法**：把 `onBack` 接回 `setBatchItems(null)` → 红。
- `DownloadBar.test.tsx` 三条：inline 来源返回后单行框有原文且 `pasteOpen === false`；paste 来源返回后粘贴框开着且 `initialText` 是原文；**取消命名方式弹窗后原文同样回来**。**破法**：不记 origin、一律回粘贴框 → 第一条红；只在批量那条路上登记 `parsedFrom` → 第三条红。

### P3 · 清洗命名认识多个歌手（⑧）

`feat(download): teach the naming prompt how to join several artists`

**改什么** —— `INFER_SONG_INFO_PROMPT` 增加一条规则：

```
- 如果有多个创作者：全部保留，用「、」分隔（例如"周杰伦、费玉清"），顺序按标题里出现的先后
```

🔴 **这是有意的行为变更，不是清理**。`prompts.ts` 的文件头写着「这些提示词的中文措辞就是接口，它们是对着真实 B 站标题调出来的，改写等于改行为」—— 所以这一条要在 commit body 里说清楚为什么改、改的是哪一条规则。

**判据**
- `prompts.test.ts` 加一条：`INFER_SONG_INFO_PROMPT` 同时含「多个创作者」与「、」。**破法**：删掉这条规则 → 红。
- **如实说清**：真实效果只有对着真模型才看得到，电脑上这条**只有单测覆盖**。真机会话里排一个**观察项**（不是判据）：找一个双人合唱的视频走一次清洗命名，看 artist 是不是 `A、B`。

### P4 · 加歌页的草稿活过一次切 tab（③）

`feat(mobile): keep the add page's draft while you look at another tab`

**改什么**
- `shell.tsx:88` 是 `{tab === '添加' && <AddTab />}` —— 切 tab 直接卸载，`text` 与 `playlistId` 当场没。同一个文件 51–53 行**已经为完全相同的原因**把 `openPlaylist` 提到了 Shell（注释：「一个每次瞄一眼设置就忘了自己在哪的详情页是会被弃用的页面」）。照这个先例来。
- Shell 持有 `addDraft: { text: string; playlistId: string | null }`，作为 prop 给 `AddTab`。分享到达仍然覆盖 `text`（`subscribeShareDraft`）—— 分享就是要盖掉草稿。提交成功后置空。
- **不落盘**：用户要的是「不退出软件就在」，内存态正好，写文件是超出要求的那一步。

**判据**
- 新增 `ui/add-draft.ts`（纯函数：提交后清空 · 分享覆盖 · 分享不清歌单选择），进 vitest include。**破法**：让分享覆盖时把 `playlistId` 也清掉 → 红。
- `AddTab` 自己 import RN，测不了 —— 判定必须落在纯模块里，这条是仓库规矩不是偷懒。
- 「切 tab 回来还在」只有设备能答，进 P11。

### P5 · 歌词滚到最后一行仍然居中（⑥）

`fix(mobile): let the last lyric line reach the middle of the screen`

**改什么** —— 症结是两行样式：`player-screen.tsx:211` 滚到 `top - height/3`，而 `lyricsBody` 只有 `paddingVertical: 12`。内容底部没有可滚空间，**最后约 2/3 屏的行根本滚不上去**，所以停住。

- 抽 `ui/lyrics-scroll.ts`（纯算术，进 vitest include）：`lyricsPadding(viewportHeight)` → 上下各半屏；`targetOffset({ tops, index, viewportHeight, lineHeight })` → 让第 index 行的**中心**落在视口中心。
- 目标从 `height/3` 改成**正中**（用户定）。上下都补 padding，首行和末行因此都能到位。
- 顺带修一个既有小 bug：`tops.current` 是不清空的 ref 数组，换歌瞬间 `index` 已变、新行还没 `onLayout`，会拿上一首的 y 滚一次。按 `lines` 引用变化清空。

**判据**
- `lyrics-scroll.test.ts`：最后一行算出的目标 y **不被 clamp 到内容末尾**；换歌后 tops 为空时返回 `null`（不滚）而不是 0。**破法**：把 `paddingBottom` 改回常数 12 → 最后一行那条红。

### P6 · 歌词中线跳转 + 手动滚动后回归（⑦）

拆两次提交。行为参考网易，按行业惯例。

#### P6a `feat(mobile): find which lyric line the middle of the screen is on`

- `ui/lyrics-scroll.ts` 扩两个纯函数：
  - `lineAtCenter(tops, scrollY, viewportHeight)` → 中线落在第几行
  - `followMachine`：`follow` / `dragging` / `settling(until)` 三态 —— `onDragBegin` · `onScrollSettled(now)` · `onTick(now)` · `onSeek()`（跳转后**立刻**回 `follow`，用户定）
- **判据**：三态迁移逐条 + 「跳转立刻回跟随，不等超时」。**破法**：让 `onSeek` 只是重置倒计时 → 红。

#### P6b `feat(mobile): seek from the lyric you scrolled to`

- `player-screen.tsx` 接线：`onScrollBeginDrag` / `onScrollEndDrag` / `onMomentumScrollEnd` / `onScroll` + `scrollEventThrottle={16}`。

- 🔵 **这里用 JS `setTimeout` 是对的，要在注释里写明白**：守卫 `check-mobile-no-js-timers.sh` 只盯 `src/player/`，而它的判准是「这个等待在熄屏时还有意义吗」—— 屏幕关了没人在看歌词，答案是没有。这正是 N4f-2 那个宽限期被**删掉**而不是搬去原生的同一条推理。
- **判据**：接线本身只有设备能答，进 P11。电脑侧的判据全在 P6a。

### P7 · 一次下载记得自己从哪来（④ 的数据层）

拆四次提交。**这是唯一一处两端同时动的改动。**

#### P7a `feat(shared,core): give a download task the origin it came from`

- `@lark/shared` 新增：

```ts
export type DownloadOrigin =
  | { kind: 'keyword'; query: string }
  | { kind: 'video'; url: string }                       // 带 ?p=
  | { kind: 'list'; list: 'favorites' | 'collection';
      title: string; url: string;                        // 合集/收藏夹自己的链接
      video_url: string;                                 // 这一条的视频链接，带 ?p=
      index: number; total: number }                     // 「3/50」
  | { kind: 'song'; song_id: string };
```
  挂到 `DownloadTaskData.origin`（`DownloadTaskInput` **不动** —— 它是「要下什么」，来源是「谁点的」，两件事）。
- `DownloadBatchGroupInput` 加可选 `source: { list: 'favorites' | 'collection'; title: string; url: string }`。
- `engine.ts` 四处入队各填 origin；**批量那处顺带把 `?p=` 补回 `input.url`** —— 它今天丢，导致多 P 视频的「重下」回到 p1。
- `index/total` 在入队时就烤进 origin，**不靠 batch 现算**：手机的记录活得比引擎那 20 个批次的环长。
- `download-labels.ts` 加两个纯函数，**两端共用一份文案**：
  - `originLabel(origin)` → `from：青花瓷` / `from：某某合集（3/50）` / `from：https://…?p=2`
  - `originCopyText(origin)` → 关键词原文 / 视频链接（**带 `p=`**）/ 歌曲的 `source_url`

**判据**
- `download-labels.test.ts`：四种 origin 的显示文案与复制文本各一条。
- `engine.test.ts`：批量入队的 `input.url` 带 `?p=`；origin 的 `index/total` 对得上。**破法**：丢掉 `page` → 红。

#### P7b `feat(daemon): carry the list a batch came from`

- `readBatchGroups` 认 `source`（严格校验，缺省合法 —— 单行与关键词组本来就没有 list 身份）。
- **协议号这一批不动**，等 P10 一次抬到 9；本批的 commit body 里写明「线协议在此变宽，号在 P10 一起走」。
- **判据**：route 测三条 —— 缺 `source` 合法 · `source` 形状不对 400 · `source` 带未知 key 400。

#### P7c `feat(gui,mobile): tell the daemon which list a batch came from`

提交侧两端一起：桌面 `BatchSelectModal` 把组的 `source`（收藏夹/合集 + 名字 + url）发出去；手机 `list-picker` / `lines-picker` 同形。

**判据**：两端各一条「提交体里带 source」。**破法**：只改一端 → 另一端红。

#### P7d `feat(gui,mobile): say where a download came from, and let it be copied`

展示侧两端一起：行标题下一行小字 `originLabel(...)` + **一颗**复制按钮（桌面 `navigator.clipboard`，手机 `expo-clipboard` —— 两个都已经在用）。

**判据**：两端各一条「复制按钮把 `originCopyText` 放进剪贴板」+ 一条「合集行的小字带 `（N/M）`」。**破法**：复制成 `taskTitle` → 红；把 `originCopyText` 对 list 改成返回合集链接 → 红。

### P8 · 桌面也把下载记录留在盘上（④ 的另一半）

拆四次提交。这条是用户点名的「两端功能统一」—— **统一到「和手机一样」为止**，包括失败行的重下（P8d）。

> **前提**：桌面今天的「下载记录」是**进程内的环**（弹窗描述原话：「这次运行里已经结束的任务」），关掉 app 就没了；只有手机在 0.1.1 ⑦ 做了 `downloads.json`。**不补这一半，④ 在桌面上只在本次运行内成立。**

#### P8a `refactor(core): move the download history into portable`

- `apps/mobile/src/downloads/history.ts` → `packages/core/src/portable/download/history.ts`。它**已经**是 RN-free（`load`/`save` 注入，只 import `@lark/shared` 和 portable 的 `StructuredLogger`），搬过去就能过 `check-core-portable.sh`。
- 手机改 import，**行为零变化**；`downloads/history.test.ts` 整份跟着搬。
- **判据**：搬之前先跑绿，搬之后同一份测试仍绿。这批不加新判据 —— 它就是一次搬家。

#### P8b `feat(daemon): keep the download history in a file, like the phone does`

- 落盘位置照手机的规矩「挨着它那个曲库」：账号库 `libraries/<32hex>/downloads.json`，local 库 `lark/downloads.json`。原子写。
- daemon 订阅任务终态喂 `observe()`；三个新端点 `GET /download/history` · `DELETE /download/history` · `DELETE /download/history/:task_id`。
- 🔴 **三条规则一字不改地照抄手机**，否则两端当场分叉：
  1. **成功的歌词续跑不进记录**（每首歌永久占两行，200 额度一半是噪音）；失败的歌词**留着**（那是全 app 唯一说得出「这首没抓到词」的地方）。
  2. **「见过」和「留着」分开记**：引擎那个环整个 launch 都还攥着那些任务，谁要是从快照重新推导，下一次状态事件就把刚删掉的行顶回来。
  3. **不自动删**，200 是文件上限不是时间窗。
- **判据**：daemon 侧三个端点 + 「删掉一条之后再来一次状态事件，它不回来」。**破法**：让 `observe` 从快照重推 → 红（这条手机上已有，桌面这份是它的第二个宿主）。

#### P8c `feat(gui): the download panel remembers what already happened`

- `DownloadPanel` 的「已结束」一节改读 history；「清除记录」从「本地隐藏」变成**真的删**；面板打开时与每次终态 `download:status` 之后刷新。
- **判据**：`DownloadPanel.test.tsx` —— 记录来自 history 而不是 `tasks`；「清除记录」发 DELETE。**破法**：仍然从 `tasks` 过滤 → 红。

#### P8d `feat(gui): ask for a failed download again, from the record`

用户定：**和手机一样**。

- 行上一颗「重下」，**只出现在没成功的行上** —— 判定用 `canRetry(record)`，P8a 之后它在 portable 里，**两端共用同一份**，这正是搬家的回报。手机当时定这条规矩的理由在桌面上更成立：歌曲的 ⋮ 菜单已经有「重新下载」，成功行再放一个就是同一件事的第二个入口，两边迟早不一致。
- 表头一颗「全部重试 N」，**只针对失败的**（取消是某人的决定，一次性撤销每一个不是这颗按钮的用途 —— 手机的原话）。串行，一次一个。
- 桌面的重放比手机简单：手机要自己走一遍识别器（`replay.ts`），桌面把 `record.input` 交回 daemon 就行 —— `url` / `keyword` 走 `POST /download/song`，`song` 走 `POST /songs/:id/redownload`。
- **记录不带命名方式**（`DownloadTaskData` 上就没有），重试按**当下**选的命名走 —— 这是手机已经定过的语义，桌面照抄，别在这里发明第二种。
- **一条下载在记录里只占一行**：重试要把被它取代的那条记录删掉，那一行的状态就是最后一次尝试的状态。

**判据**：`DownloadPanel.test.tsx` 三条 —— 成功行没有「重下」、失败行有、「全部重试」只数失败的。**破法**：给成功行也画上 → 第一条红；把「全部重试」改成数所有终态行 → 第三条红。

## 7 · 实施修订

（按仓库规矩，实施中的修订**追加**在这一节，不改上面的原文。）

### 修订 1 · P9 桌面歌词：拖拽区换成 pointer 手势（2026-08-28，桌面验收 §2.5 判据 19 红）

**现象**：歌词窗上悬停，控制条和右下角把手一次都不出现；在歌词上右键反而弹出一个 macOS 的窗口菜单。设置项、锁定、关闭回写、重启后仍开着、恢复默认位置——**其余十一条全过**，坏的只有「鼠标移上去」这一条通路。

**根因**：`.lyrics-draggable { -webkit-app-region: drag }` 铺在根节点上，而 `onMouseEnter` 挂的就是那个根节点。拖拽区吞掉区域内的全部鼠标事件，`hovering` 永远是 `false`。`no-drag` 只能给**已经画出来**的子元素打洞，而控制条恰恰是 hover 之后才画的——鸡生蛋。右键那个菜单是同一件事的另一面：macOS 把拖拽区当标题栏。

**改法**（用户三选三，都取推荐项）：

- **窗口由 pointer 拖**，`-webkit-app-region` 从这个窗口彻底移除。renderer 只说「按下了 / 动了 / 松了」，main 读 `screen.getCursorScreenPoint()`，按**按下那一刻的锚点**算新 bounds（`main/desktop-lyrics-gesture.ts`）。锚点不是好看写法而是必要的：`setBounds` 是请求不是赋值（macOS 不让窗口进菜单栏），拿返回的 bounds 重新锚会把一次拒绝折进后面每一步，窗口从此落后光标一截。
- **右下角把手自己 resize**，不再指望窗口边缘——Electron 文档写着透明窗口不可 resize，那个把手原本是句空承诺。下限 200×40，就是 `DESKTOP_LYRICS_BOUNDS` 那两个数，挪到人真够得到的地方。
- **悬停时画出窗口的范围**（用户提的）：深色蒙版 + 一圈浅描边 + 圆角，和控制条同一套观感，跟着 hover 一起来去。这个窗口除了字全透明，此前没有任何东西说得出「能抓的是哪一块」。
- 控制条自己 `stopPropagation` 一次 pointerdown：按「A+」再抖一下不该把窗口拖走。

**判据**：`desktop-lyrics-gesture.test.ts` 八条（含「平台拒绝之后仍跟得上光标」「不许中途换 kind」「resize 撞下限」），`DesktopLyrics.test.tsx` 新增七条（拖动三段、控制条上按下不拖、把手是 resize、锁定后什么都不启动、范围提示只在 hover 时且锁定时没有）。**六条破法逐条验过红。**

🔴 **另有一条判据是空的，验破法时才发现**：想在渲染进程测「样式表里没有 drag 区」，`import css from './lyrics.css?raw'` 拿到的是**空串**——vitest 默认把 CSS import 桩掉。把 drag 区放回去，那条断言照样绿。删掉它，改成 `just check` 的第十四条守卫 `check-lyrics-no-drag-region.sh`（守卫红过、还原后绿）。守卫十三 → **十四**（`INVARIANTS` §2 顺手补上一直漏记的 IME 那条）。

测试 3512 → **3527**。`just check` 绿。**待用户复验**：§2.5 的 19 与 21，外加两条这次新出现的——把手能不能真的改大小、范围提示看不看得清。
