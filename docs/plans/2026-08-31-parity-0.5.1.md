## 0 · 这一批是什么

用户在发版前要求做一次「同一功能在两端有什么差异」的普查。查出的差异分三类：**有意且已记录**（不动）、**漂移**（这一批处理三条）、**文档与代码不符**（这一批改文档）。

三件事：

1. **手机的分P 提交目标改成和桌面一致** —— 桌面分P 组是 `target: {kind:'new', name: 标题}`（新建歌单、标题可改），手机是「存到当前目标、不建歌单、标题只读」。`INVARIANTS.md` §3 明写两端一致，**代码不是**。
2. **桌面补下载失败自动重试** —— 0.1.1 ⑧ 只做了手机（`apps/mobile/src/downloads/retry.ts`），桌面从来没有另一半。白名单与次数语义搬进 portable，两端共用一份。
3. **文档改到与代码一致** —— `INVARIANTS.md` §7 第一条已过期；N4i 决策 f 的两条「不做」只活在子计划里，没进 backlog 的 E 节；这次没做的对齐项进 backlog。

**普查全表在对话里给过一次**，结论按三类落到了文档：有意分叉的出处逐条核对过（§7 / 子计划 / backlog E），漂移两条这一批修，其余四条进 backlog（§6）。

**不在这一批**（普查查出来、明确留给下一轮，见 §6）：桌面的「上次听到哪」· `[重复]` 标记搬到手机 · 手机歌曲页多选加「下载」· C11/C12 的两份 row 与三份 StyleSheet。

## 2 · 三件事各自怎么做

### 2.1 手机分P（P1）

**现状（file:line）**

- 桌面：`packages/gui/src/renderer/src/components/batch-groups.ts:114` → `target: { kind: 'new', name: group.title }`；标题默认 `data.title`（`BatchSelectModal.tsx:247`），行内可改（`:509`）。
- 手机：`apps/mobile/src/ui/add-tab.tsx:357` 把当前「存到」当成 target 传给 `PartsPicker`；`ui/parts-picker.tsx` 用它 `submitBatch({ target, items })`，header 只有一行只读的 `存到 · {targetName}`。
- 收藏夹/合集在手机上**已经是**新建歌单（`downloads/preflight.ts:453` `submitListBatch` → `{kind:'new', name}`），**只有分P 走散了**。

**改法**

1. 新文件 `packages/core/src/portable/download/batch-groups.ts`：
   ```ts
   export function partsGroupPayload(
     bvid: string, title: string, pages: readonly number[], naming: DownloadNamingMode,
   ): DownloadBatchGroupInput
   ```
   —— 返回 `{ target: {kind:'new', name: title}, items: pages.map(...) }`，**不带 `source`**（一个视频不是一个列表，0.5.0 ④）；每个 item `title: null`（分P 的名字由 pipeline 从 page list 读，`INVARIANTS.md` §3）。
2. 桌面 `batch-groups.ts` 的 `groupPayload` 在 `kind === 'parts'` 分支改为调它——**行为零变化**，是把同一句话收成一处。
3. 手机 `ui/parts-picker.tsx`：
   - 加 `name` state，`data` 到达时置为 `data.title`；
   - header 里的 `存到 · {targetName}` 换成一个 `TextInput`（照 `ui/list-picker.tsx` 的写法，同样的样式）；
   - `onSubmit` 改成 `submitBatch(deps, partsGroupPayload(bvid, name, pages, mode))`。
4. `ui/add-tab.tsx`：不再给 `PartsPicker` 传 `target` / `targetName`。
5. `apps/mobile/src/downloads/parts.ts` 的 `partItems` 被 `partsGroupPayload` 取代，删掉。

**判据（怎么变红）**

| # | 判据 | 破法 |
|---|---|---|
| 1 | `partsGroupPayload` 产出 `target.kind === 'new'` 且 `name` 是传进去的标题 | 把它改回 `{kind:'all'}` → 红 |
| 2 | 每个 item 是 `{kind:'video', bvid, page, title: null, naming}` | 给 item 填上 part 标题 → 红（**这条是 §3「两个来源写同一个字符串迟早走散」的守门人**） |
| 3 | 桌面 `groupPayload` 对 parts 组的输出与 `partsGroupPayload` 逐字段相同 | 桌面分支改回自己拼 → 只要两边不一致就红 |
| 4 | 分P 组不带 `source` | 加上 → 红 |

🔴 **判据 1–2 必须落在 portable 的单测里，不是组件测试**：`apps/mobile/vitest.config.ts` 的白名单挡住任何 import react-native 的文件，判定留在组件里等于**没有测试**（`INVARIANTS.md` §7 最后一条）。这也是决策 b 的第二个理由。

**真机要看的**（发版前那次会话里带上，见 §4）：粘一个多P 链接 → 回车 → 分P 页出现，**顶上是可改的歌单名（默认视频标题）**、零勾选 → 勾两个 → 下载 → **歌单页多出一个以视频标题命名的歌单，里面两首**。

### 2.2 桌面自动重试（P2）

**判定搬进 portable**

`apps/mobile/src/downloads/retry.ts` 里 `RETRYABLE_CODES`（四个码，以及注释里逐条写明「为什么另外九个不重试」）、`RETRY_LIMITS`、`DEFAULT_RETRY_LIMIT`、`shouldRetry` 原样搬到 `packages/core/src/portable/download/retry.ts`，**注释一起搬**——那段注释是这个功能的全部（「白名单错了在两个方向上都是静默的」）。手机侧只留 `readRetryLimit` / `writeRetryLimit`（device settings 的读写）。

**引擎新增 `enqueueRetry(taskId)`**

```
enqueueRetry(taskId: string): DownloadTaskData | null
```
- 拿自己的 `TaskRecord`（`task-data.ts:70` 有 `target`），按 kind 分派：
  `download` → `enqueueDownload({target, playlistIds, url})`；`redownload` → `enqueueRedownload(songId)`；`ensure-file` → `enqueueEnsureFile(songId)`；`lyrics` → **返回 null**。
- 未知 id → `null`。

**为什么不是「重放 record 的文本」（手机今天的做法）**：`DownloadRecord` 刻意**不带 naming mode**（`history.ts:70`），手机靠「现在设置页记着的那个」补上（`replay-runtime.ts:44`）。daemon 没有这种记忆——桌面的命名模式在渲染进程的 localStorage 里（`lib/naming-mode.ts`）。而 task 自己的 `target` 里**已经有** `naming`，重放它既不需要记忆也不需要网络（短链不用再展开一次）。

**daemon 侧 `packages/daemon/src/download-retry.ts`**（照抄手机 `retry-runtime.ts` 的形状）：

- 在 `boot.ts` 的 `callbacks.onStatus` 里，`downloadHistory.observe([task])` 之后调一次；
- 只看终态失败；`judged: Set<taskId>` 防止同一条被数两次（`onStatus` 会为同一个终态 task 触发多次）；
- `attempts: Map<下一个 task id, 已试次数>`，**按链条计数**，重试发出时把计数改挂到新 task 上——注释里那句「key 成任何派生值都会重置计数，那不是『多试一次』而是一个循环」原样保留；
- `MAX_AUTOMATIC_RETRIES = 50` 兜底，触到就 log；
- 成功排上新 task 之后 `downloadHistory.remove(旧 id)`（**一条链一行**，`supersededRecord` 的同一条规则）；
- 🔴 **`queueMicrotask` 里执行**：`onStatus` 是引擎自己发状态时同步调用的，在回调里直接 enqueue 是在 worker 正在跑的时候动 `#tasks`/`#queue`。手机那边天然隔了一跳（hub tick），daemon 这边要自己隔。

**配置**

- `packages/shared/src/config-types.ts`：`DownloadConfig { retry_limit: number }`，进 `LarkConfig` 与 `ConfigPatchRequest`；
- `packages/core/src/config/index.ts`：默认 `{ retry_limit: 1 }`、`sanitize` 收敛到菜单内、Public 投影带上；
- daemon `PATCH /config` 校验：不在 `RETRY_LIMITS` 里 → 400（与 `log.level` / `theme.mode` 同形，域在 shared、两个消费方相反策略）;
- GUI 设置页：`GeneralTab.tsx` 加一段「下载」，一个 `Select`（不重试 / 1 次 / 2 次 / 3 次），`draft.ts` 加 `retryLimit` 字段与 diff 分支——**照既有的「只发人碰过的字段」写法**（`INVARIANTS.md` §3）。

**判据（怎么变红）**

| # | 判据 | 破法 |
|---|---|---|
| 5 | `shouldRetry` 对四个白名单码在 `attempts <= limit` 时为真 | 删一个码 → 红 |
| 6 | 反测：`CACHE_LIMIT` / `BILIBILI_RISK_CONTROL` / `SOURCE_GONE` / `LLM_FAILED` 一律不重试 | 把 `RETRYABLE_CODES` 换成「所有码」→ 红 |
| 7 | `enqueueRetry` 对 lyrics task 返回 null 且不入队 | 让它也重放 → 红 |
| 8 | `enqueueRetry` 重放的 target 与原 task **逐字段相同**（含 `naming`） | 重新用默认 naming 拼一个 → 红 |
| 9 | daemon：一个 `DOWNLOAD_TIMEOUT` 失败在 limit=1 下产生**恰好一个**新 task，limit=0 下产生**零个** | 把计数键成 url → 无限重试，判据看到 >1 → 红 |
| 10 | daemon：重试排上之后，旧 record 不在 `GET /download/history` 里，新 record 在 | 不删旧行 → 记录翻倍 → 红 |
| 11 | daemon：`PATCH /config` 收 `download.retry_limit = 7` → 400 | 只 clamp 不拒 → 红 |
| 12 | `accept-gui` 新增**两条**（实做时从一条长到两条）：daemon 存得下 `download.retry_limit`（PATCH → 重读 == 2）· 给它一个 `7` 是 **400 `INVALID_CONFIG`** 且原值不动 | 这两条答的是**协议**那一半：daemon 不认这个段 → `INVALID_CONFIG` → 红；只 clamp 不拒 → 第二条红。源码判据答不了。**不走设置页**——CDP 够得到渲染进程，但那个对话框这套件不驱动，页面那一层归人工验收 |

`accept-gui` **18 → 20**，五套合计 **132 → 134**。

### 2.3 手机也改成重放 target（决策 g ✅）

**做**：手机 `retry-runtime.ts` 的自动那条路改调 `engine.enqueueRetry(task.id)`；**手动 `重下` 不动**（那条路上人按了按钮，「今天的答案」是对的）。

**理由**：今天手机的自动重试会用**此刻**设置页记着的命名模式重下。一次超时之后如果人在 添加 页把 chip 从「原标题」拨到「清洗命名」，那首歌会以另一个名字落库——**没有人要求过这件事**。自动重试是同一个请求的延续，不是一次新的决定。

**代价**：手机行为变了 ⇒ 真机那一轮要加一条（§4）。

**实做补记**：`retry-runtime.ts` 因此不再需要 `replay` / `planRetry` / `recordOf`，`replay-runtime.ts` 从两个调用方降为一个（只剩手动 `重下`）——它的文件头原本写着「TWO CALLERS NOW, WHICH IS WHY THIS EXISTS」，已改写，**别让一份注释替一个已经不成立的结构辩护**。
